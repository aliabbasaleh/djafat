# SPEC-017-02 — Passer la commande reçue par WhatsApp

## Comportement observable

- Webhook WhatsApp existant (`POST /v1/auth/whatsapp/webhook`, signé) : un
  texte commençant par `DJF1` émet `order_message.received { phone, text }`
  (mêmes règles de fraîcheur, de numéro et de message traité une seule fois
  qu'une demande de code).
- `admin` (`OfflineOrdersService`) passe la commande et répond par WhatsApp
  (texte libre dans la fenêtre de 24 h ; en développement, gardé dans Redis
  `wa:mock:reply:<numéro>`).

## Règles métier

- R1 — Compte existant seulement (`UsersService.findByPhone`) ; adresse du
  carnet de ce compte seulement.
- R2 — Chaque préfixe doit désigner un seul plat de la carte, une seule
  option du plat, une seule adresse ; sinon refus.
- R3 — Panier remplacé, `createOrder(client, K, adresse)` : la même clé que
  l'application, donc une seule commande.
- R4 — Paiement choisi par capacité : espèces (`collectedOnDelivery`, soumis
  au plafond FEAT-015) ou Airtel (`matchedByTransferReceipt`, depuis le numéro
  qui écrit), clé `offline:K`. Plafond dépassé : commande en attente de
  paiement, la réponse le dit.
- R5 — Code livreur préparé (FEAT-012) et donné dans la réponse.
- R6 — Audit `ORDER_PLACED_BY_MESSAGE` à la création seulement.

## Scénarios

### SPEC-017-02-SC01 — commande passée

Critères : FEAT-017-AC02

- **Étant donné** un compte, un message valide, paiement espèces
- **Quand** il arrive
- **Alors** commande créée avec la clé K, paiement à la livraison, audit, réponse avec numéro, total et code

### SPEC-017-02-SC02 — Airtel

Critères : FEAT-017-AC02

- **Étant donné** un message `P:A`
- **Quand** il arrive
- **Alors** paiement Airtel depuis ce numéro, consignes dans la réponse

### SPEC-017-02-SC03 — déjà passée par l'application

Critères : FEAT-017-AC03

- **Étant donné** une commande déjà créée avec la même clé
- **Quand** le message arrive
- **Alors** la même commande, pas de second paiement, pas de second audit

### SPEC-017-02-SC04 — introuvable

Critères : FEAT-017-AC04

- **Étant donné** un numéro sans compte, un message abîmé, un restaurant, plat ou adresse inconnu
- **Quand** il arrive
- **Alors** rien n'est commandé ; une réponse explique

### SPEC-017-02-SC05 — refusée par les règles

Critères : FEAT-017-AC04

- **Étant donné** un restaurant fermé, ou un plafond espèces dépassé
- **Quand** le message arrive
- **Alors** la réponse le dit (commande refusée, ou en attente de paiement Airtel)

### SPEC-017-02-SC06 — parcours réel [evidence: manual]

Critères : FEAT-017-AC02, FEAT-017-AC03

- **Étant donné** l'API réelle et un client avec une adresse
- **Quand** son message WhatsApp signé arrive, puis l'application envoie la même commande
- **Alors** une seule commande ; voir `e2e-demo.md`

## Erreurs et cas limites

Une erreur inattendue est journalisée ; le webhook répond toujours 200 (Meta ne renvoie pas).

## Contrats API et données

Pas de route nouvelle (webhook WhatsApp existant) ; événement `order_message.received` ; aucune table.

## Autorisations

Signature Meta du webhook ; le numéro qui écrit doit être celui d'un compte existant.

## UI et accessibilité

Réponses WhatsApp en français simple.
