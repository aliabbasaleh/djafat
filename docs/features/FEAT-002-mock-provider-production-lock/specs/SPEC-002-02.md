# SPEC-002-02 — Le seed n'active pas les fournisseurs sandbox en production

## Comportement observable

Aujourd'hui, `apps/api/prisma/seed.ts` :

- écrit `mock` avec `active: true` (`:193`) ;
- crée une configuration de disponibilité pour `['cash', 'mock']` (`:217`) ;
- active le drapeau `mock_payment_provider` (`:289-292`).

Tout cela se fait sans regarder `NODE_ENV`. Après : ces trois effets dépendent de
l'environnement, et la liste des fournisseurs sandbox est lue dans leurs capacités
(même source que SPEC-002-01).

## Règles métier

- R1 — Avec `NODE_ENV=production`, un fournisseur sandbox est écrit `active: false`, n'obtient aucune configuration de disponibilité, et le drapeau `mock_payment_provider` est désactivé.
- R2 — Hors production, le seed est inchangé.
- R3 — Le seed reste idempotent (`upsert`) : rejoué en production sur une base seedée en dev, il désactive `mock` **et désactive (`enabled: false`) ses configurations de disponibilité existantes** (v2 : écart trouvé en exécution réelle, la v1 ne laissait que la ligne fournisseur inactive).

## Scénarios

### SPEC-002-02-SC01 — plan de seed en production

Critères : FEAT-002-AC05

- **Étant donné** l'environnement de production
- **Quand** le plan d'activation des fournisseurs est calculé
- **Alors** `mock` est inactif et sans configuration, `cash` est actif avec configuration, et le drapeau mock est désactivé

### SPEC-002-02-SC02 — plan de seed hors production

Critères : FEAT-002-AC04

- **Étant donné** l'environnement de développement
- **Quand** le plan d'activation est calculé
- **Alors** `cash` et `mock` sont actifs avec configuration, et le drapeau mock est activé (comportement actuel)

### SPEC-002-02-SC03 — la liste sandbox du seed vient des capacités des fournisseurs

Critères : FEAT-002-AC05

- **Étant donné** les fournisseurs réellement enregistrés par l'API
- **Quand** on demande les codes sandbox
- **Alors** on obtient exactement les codes dont les capacités déclarent `sandboxOnly: true` (`mock`)

### SPEC-002-02-SC04 — re-seed en production d'une base seedée en dev

Critères : FEAT-002-AC05

- **Étant donné** une base déjà seedée hors production (mock actif, configuration de disponibilité `mock` activée)
- **Quand** le plan de production est calculé pour la re-seeder
- **Alors** il demande de désactiver les configurations existantes de `mock`, et seulement elles (`cash` reste activé)

## Erreurs et cas limites

Base de production déjà seedée avec `mock` actif : un nouveau seed la corrige
(upsert R3). Et même sans re-seed, SPEC-002-01 garantit que l'API l'ignore.

## Contrats API et données

Aucun changement de schéma. Les tables `payment_providers`, `payment_provider_configs`
et `feature_flags` sont écrites différemment selon l'environnement.
