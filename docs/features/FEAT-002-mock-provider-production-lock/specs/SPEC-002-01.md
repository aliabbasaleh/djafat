# SPEC-002-01 — Les fournisseurs « sandbox only » ne sont pas enregistrés en production

## Comportement observable

Aujourd'hui (`apps/api/src/modules/payments/payments.module.ts:31-36`), le registre
reçoit toujours `[cash, mock]`. Toutes les entrées passent par le registre :
`createPayment` (`payments.service.ts:80`), `handleWebhook` (`:163`) et
`listAvailablePaymentMethods` (`:806`) testent `registry.has(code)`. Un fournisseur
absent du registre est donc refusé partout avec `PROVIDER_UNAVAILABLE` (404) et
disparaît de la liste.

Après : un fournisseur déclare `sandboxOnly: true` dans ses `ProviderCapabilities`.
En production (`AppConfigService.isProduction`), le module ne l'enregistre pas.

## Règles métier

- R1 — En production, un fournisseur dont les capacités déclarent `sandboxOnly: true` n'est jamais enregistré.
- R2 — Hors production, tous les fournisseurs sont enregistrés (comportement actuel).
- R3 — La décision est pilotée par la capacité déclarée, jamais par le code du fournisseur.
- R4 — `mock` déclare `sandboxOnly: true` ; `cash` ne le déclare pas.

## Scénarios

### SPEC-002-01-SC01 — en production, le registre exclut les fournisseurs sandbox

Critères : FEAT-002-AC01, FEAT-002-AC03

- **Étant donné** les fournisseurs `cash` et `mock`, et l'environnement de production
- **Quand** le registre est construit
- **Alors** il contient `cash` mais pas `mock`, et `get("mock")` lève `PROVIDER_UNAVAILABLE`

### SPEC-002-01-SC02 — en production, un paiement mock est refusé sans rien écrire

Critères : FEAT-002-AC01

- **Étant donné** une commande en attente de paiement et le registre de production
- **Quand** le client crée un paiement avec `providerCode: "mock"`
- **Alors** la création échoue avec `PROVIDER_UNAVAILABLE` et aucune ligne `payments` n'existe

### SPEC-002-01-SC03 — en production, un webhook mock signé est rejeté

Critères : FEAT-002-AC02

- **Étant donné** un paiement `mock` en attente et un webhook correctement signé avec le secret de développement
- **Quand** le webhook est reçu par l'API de production
- **Alors** il est refusé avec `PROVIDER_UNAVAILABLE` et le paiement reste `pending`

### SPEC-002-01-SC04 — la liste des moyens de paiement ignore mock en production [evidence: review]

Critères : FEAT-002-AC03

- **Étant donné** une configuration en base qui active `mock` pour la ville
- **Quand** `listAvailablePaymentMethods` est appelé en production
- **Alors** `mock` n'apparaît pas, car la boucle saute tout fournisseur absent du registre (`payments.service.ts:806`). Couvert par SC01 au niveau du registre, et vérifié en revue pour la boucle

### SPEC-002-01-SC05 — hors production, mock reste disponible

Critères : FEAT-002-AC04

- **Étant donné** les fournisseurs `cash` et `mock`, en développement puis en test
- **Quand** le registre est construit
- **Alors** il contient `cash` et `mock`

### SPEC-002-01-SC06 — la décision vient des capacités, pas du code fournisseur

Critères : FEAT-002-AC01, FEAT-002-AC04

- **Étant donné** un fournisseur fictif de code quelconque déclarant `sandboxOnly: true`, et un autre ne le déclarant pas
- **Quand** la sélection est faite en production
- **Alors** seul le second est retenu

## Erreurs et cas limites

- Liste vide en production si tous les fournisseurs étaient sandbox : impossible
  aujourd'hui (`cash` n'est pas sandbox), et non bloquant (le registre accepte une liste vide).
- `sandboxOnly` absent = `false` (champ optionnel) : les fournisseurs futurs sont
  autorisés par défaut, sauf déclaration explicite.

## Contrats API et données

- `ProviderCapabilities.sandboxOnly?: boolean` (**nouveau**, optionnel, `packages/types/src/payment-provider.ts`).
- Aucune route, table ou migration modifiée. Réponse d'erreur existante : 404 `PROVIDER_UNAVAILABLE`.
