# SPEC-010-02 — Affecter un transfert reçu au reversement d'un livreur

## Comportement observable

`POST /v1/payments/mobile-money/receipts/:id/remit { courierId }` (équipe) → 200 `{ receipt, cashHeld }`. Le transfert devient `matched` avec `courier_id`, le grand livre enregistre le reversement, et `courier.cash_remitted` est émis.

## Règles métier

- R1 — Une seule transaction : mise à jour conditionnelle `unmatched → matched` avec `courier_id`, puis groupe `cash_reconciliation` (débit `PSP_CLEARING`, crédit `CASH_FLOAT:<livreur>`, montant du transfert, clé `remittance:<transfert>`).
- R2 — Montant > argent détenu (lu dans la même transaction) → 409 `REMITTANCE_EXCEEDS_CASH_HELD`, rien n'est écrit (Q05).
- R3 — Transfert déjà utilisé (paiement ou reversement) → 409 `PAYMENT_INVALID_STATE`, rien n'est écrit.
- R4 — Base : un transfert `matched` porte **soit** un paiement **soit** un livreur, jamais les deux ni aucun.

## Scénarios

### SPEC-010-02-SC01 — reversement enregistré

Critères : FEAT-010-AC03

- **Étant donné** un transfert non rapproché de 20 000 XAF, et un livreur L détenant 31 000 XAF
- **Quand** l'équipe l'affecte à L
- **Alors** le transfert est `matched` avec L, un groupe `cash_reconciliation` équilibré est passé avec la clé `remittance:<id>`, et `courier.cash_remitted` est émis pour L

### SPEC-010-02-SC02 — reversement trop élevé : refusé

Critères : FEAT-010-AC03

- **Étant donné** un livreur détenant 5 000 XAF
- **Quand** un transfert de 20 000 XAF lui est affecté
- **Alors** 409 `REMITTANCE_EXCEEDS_CASH_HELD`, le transfert reste `unmatched`, rien n'est passé au grand livre

### SPEC-010-02-SC03 — transfert déjà utilisé : refusé

Critères : FEAT-010-AC03

- **Étant donné** un transfert déjà rapproché
- **Quand** il est affecté à un livreur
- **Alors** 409 `PAYMENT_INVALID_STATE`, rien n'est passé au grand livre

### SPEC-010-02-SC04 — garanties de la base [evidence: manual]

Critères : FEAT-010-AC03

- **Étant donné** la migration appliquée
- **Quand** on insère un transfert `matched` avec un paiement **et** un livreur, ou sans aucun des deux
- **Alors** l'insertion est refusée ; voir `e2e-demo.md`

## Erreurs et cas limites

Livreur inconnu ou sans espèces → il détient 0 → 409 `REMITTANCE_EXCEEDS_CASH_HELD` (R2), sans que `payments` lise la table des livreurs (version 2 : la version 1 prévoyait un 404). Devise différente : même cas. Deux reversements simultanés pour un même livreur sont sérialisés par un verrou transactionnel PostgreSQL : le second voit le solde déjà diminué.
