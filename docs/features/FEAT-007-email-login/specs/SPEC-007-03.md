# SPEC-007-03 — Se connecter avec un code reçu par e-mail

## Comportement observable

Nouvelles routes publiques, limitées en débit :

- `POST /v1/auth/email/request { email }` → toujours 202.
- `POST /v1/auth/email/verify { email, code }` → 200 avec `{ access, refresh, user, … }`,
  comme `otp/verify`.

## Règles métier

- R1 — Un code de connexion n'est envoyé que si l'adresse est vérifiée sur un compte non supprimé. Sinon, rien n'est envoyé et la réponse est identique (pas d'énumération des comptes).
- R2 — La vérification réussie ouvre une session par le même chemin que la connexion par SMS (session, jeton, audit `AUTH_LOGIN_SUCCESS`).
- R3 — Un compte non actif est refusé en `ACCOUNT_INACTIVE`, avec un audit `AUTH_LOGIN_FAILURE`.
- R4 — Un code e-mail ne crée jamais de compte (le téléphone reste requis).

## Scénarios

### SPEC-007-03-SC01 — adresse vérifiée : code envoyé

Critères : FEAT-007-AC03

- **Étant donné** un compte actif avec l'adresse vérifiée `awa@example.td`
- **Quand** une connexion est demandée pour `AWA@example.td`
- **Alors** un code `login` est demandé pour la cible e-mail `awa@example.td`

### SPEC-007-03-SC02 — adresse inconnue ou non vérifiée : rien n'est envoyé

Critères : FEAT-007-AC03

- **Étant donné** une adresse sans compte, puis une adresse présente mais non vérifiée
- **Quand** une connexion est demandée
- **Alors** l'appel réussit sans erreur, et aucun code n'est demandé

### SPEC-007-03-SC03 — bon code : session ouverte sur le bon compte

Critères : FEAT-007-AC04

- **Étant donné** un code valide pour `awa@example.td`, adresse vérifiée du compte U
- **Quand** il est vérifié
- **Alors** une session est créée pour U, et la réponse contient des jetons d'accès et de rafraîchissement et le `MeDto` de U

### SPEC-007-03-SC04 — compte inactif refusé

Critères : FEAT-007-AC04

- **Étant donné** un code valide pour l'adresse d'un compte suspendu
- **Quand** il est vérifié
- **Alors** la connexion est refusée en `ACCOUNT_INACTIVE` et aucune session n'est créée

### SPEC-007-03-SC05 — code faux ou adresse sans compte

Critères : FEAT-007-AC04, FEAT-007-AC06

- **Étant donné** un code refusé par le service, puis un code valide pour une adresse qui n'est plus vérifiée sur aucun compte
- **Quand** ils sont vérifiés
- **Alors** les deux sont refusés en `OTP_INVALID` et aucune session n'est créée

### SPEC-007-03-SC06 — de bout en bout [evidence: manual]

Critères : FEAT-007-AC03, FEAT-007-AC04

- **Étant donné** l'API réelle et le compte de SPEC-007-02-SC05
- **Quand** il se déconnecte puis se reconnecte par code e-mail
- **Alors** `GET /v1/me` répond 200 sur le même compte ; voir `e2e-demo.md`

## Erreurs et cas limites

La demande de connexion consomme la limite par IP même pour une adresse inconnue,
pour qu'on ne puisse pas sonder en masse.

## Contrats API et données

Routes **nouvelles** : `POST /v1/auth/email/request` et `POST /v1/auth/email/verify`. Réponse de vérification identique à `POST /v1/auth/otp/verify`.
