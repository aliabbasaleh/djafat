# SPEC-007-02 — Ajouter et vérifier un e-mail sur son compte

## Comportement observable

Nouvelles routes, réservées à un utilisateur authentifié :

- `POST /v1/me/email { email }` → 202. Un code `verify_email` part vers l'adresse.
- `POST /v1/me/email/verify { email, code }` → 200 avec le `MeDto`. L'e-mail est
  enregistré, avec `email_verified_at` à maintenant.

`OtpService` est généralisé : une demande vise désormais une cible `{ channel, target }`.
`requestOtp` et `verifyOtp` (SMS) gardent leur signature.

## Règles métier

- R1 — L'adresse est normalisée (espaces retirés, minuscules) et validée, 254 caractères au plus.
- R2 — Mêmes protections que les codes SMS : hachage HMAC, TTL, essais par code, limite de demandes par adresse et par IP, verrou durable par adresse, audit.
- R3 — Le bon code enregistre l'adresse comme vérifiée ; un mauvais code est refusé en `OTP_INVALID`.
- R4 — Une adresse déjà utilisée par un autre compte non supprimé est refusée en 409 `EMAIL_ALREADY_USED`. Le code est quand même consommé.

## Scénarios

### SPEC-007-02-SC01 — demande de vérification

Critères : FEAT-007-AC01

- **Étant donné** un utilisateur connecté
- **Quand** il demande la vérification de ` Awa@Example.TD`
- **Alors** un code `verify_email` est demandé pour la cible e-mail `awa@example.td`

### SPEC-007-02-SC02 — bon code : adresse vérifiée

Critères : FEAT-007-AC02

- **Étant donné** un code valide pour `awa@example.td`
- **Quand** l'utilisateur le confirme
- **Alors** son compte porte `email = awa@example.td` et une date `emailVerifiedAt`

### SPEC-007-02-SC03 — mauvais code

Critères : FEAT-007-AC02

- **Étant donné** un code faux
- **Quand** l'utilisateur le confirme
- **Alors** la vérification est refusée en `OTP_INVALID` et le compte n'est pas modifié

### SPEC-007-02-SC04 — adresse déjà prise

Critères : FEAT-007-AC02

- **Étant donné** `awa@example.td` déjà enregistrée sur un autre compte
- **Quand** l'utilisateur confirme un code valide pour cette adresse
- **Alors** la confirmation est refusée en 409 `EMAIL_ALREADY_USED`

### SPEC-007-02-SC05 — de bout en bout sur une vraie base [evidence: manual]

Critères : FEAT-007-AC01, FEAT-007-AC02, FEAT-007-AC06

- **Étant donné** l'API réelle, PostgreSQL migré jusqu'à 0030, Redis, et un serveur SMTP local
- **Quand** l'utilisateur ajoute son e-mail, reçoit le code par SMTP et le confirme
- **Alors** `GET /v1/me` renvoie l'adresse ; un code faux répété déclenche le verrou ; voir `e2e-demo.md`

## Erreurs et cas limites

`email` invalide → 422 `VALIDATION_ERROR`. Changer d'adresse se fait de la même façon : la nouvelle remplace l'ancienne une fois vérifiée.

## Contrats API et données

- Routes **nouvelles** : `POST /v1/me/email` et `POST /v1/me/email/verify`.
- **Migration 0030** :
  - `otp_codes.phone` → `target` ; nouvelle colonne `channel` (`sms` | `email`) ;
  - la contrainte sur `purpose` accepte `verify_email` ;
  - `phone_auth_locks` → `auth_target_locks` (`phone` → `target`).

## Autorisations

`@RequireAuth()` : l'utilisateur agit sur son propre compte uniquement.
