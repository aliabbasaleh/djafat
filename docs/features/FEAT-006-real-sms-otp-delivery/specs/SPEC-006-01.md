# SPEC-006-01 — Envoi du code par une passerelle SMS HTTP

## Comportement observable

Aujourd'hui, `OtpService.requestOtp` (`apps/api/src/modules/auth/otp.service.ts:89`)
appelle `delivery.send(...)`, et le seul fournisseur branché est
`MockOtpDeliveryProvider` (`auth.module.ts:45`).

Après : un nouvel adaptateur `HttpSmsOtpDeliveryProvider` envoie
`POST <SMS_HTTP_URL>` avec :

- les en-têtes `content-type: application/json` et, si une clé est configurée,
  `authorization: Bearer <SMS_HTTP_API_KEY>` ;
- le corps `{ "to": "+235…", "from": "<SMS_SENDER_ID>", "body": "<texte>" }`.

Le texte vient d'une fonction pure `otpSmsText(code, ttlSeconds)`.

## Règles métier

- R1 — Texte : `DJAFAT : votre code est <code>. Valable <n> min. Ne le communiquez a personne.` en ASCII, moins de 160 caractères, avec `<n>` = la durée de validité arrondie à la minute supérieure, au moins 1.
- R2 — Toute réponse 2xx est un succès.
- R3 — Une erreur réseau, un délai dépassé (5 s) ou une réponse 5xx donne lieu à un seul nouvel essai. Une réponse 4xx n'est jamais réessayée.
- R4 — Un échec final lève une erreur 503 `OTP_DELIVERY_FAILED` (« Impossible d'envoyer le SMS, réessayez dans un instant »).
- R5 — Ni le code, ni le corps du SMS, ni la clé ne sont jamais journalisés. Le numéro n'apparaît que masqué.

## Scénarios

### SPEC-006-01-SC01 — envoi nominal vers la passerelle

Critères : FEAT-006-AC01

- **Étant donné** une passerelle HTTP locale, `SMS_SENDER_ID=DJAFAT` et `SMS_HTTP_API_KEY=k-123`
- **Quand** le code `482913` est envoyé au `+23566000099`, valable 300 s
- **Alors** la passerelle reçoit une seule requête `POST` avec `authorization: Bearer k-123` et le corps `{ to: "+23566000099", from: "DJAFAT", body }`, où `body` contient `482913`

### SPEC-006-01-SC02 — texte du SMS

Critères : FEAT-006-AC02

- **Étant donné** le code `482913` valable 300 s, puis 90 s
- **Quand** le texte est produit
- **Alors** il vaut exactement `DJAFAT : votre code est 482913. Valable 5 min. Ne le communiquez a personne.`, puis indique `Valable 2 min`. Il est en ASCII et fait moins de 160 caractères

### SPEC-006-01-SC03 — une erreur serveur passagère est réessayée une fois

Critères : FEAT-006-AC03

- **Étant donné** une passerelle qui répond 503 puis 202
- **Quand** un code est envoyé
- **Alors** l'envoi réussit, avec exactement 2 requêtes reçues

### SPEC-006-01-SC04 — échec persistant : 503 OTP_DELIVERY_FAILED

Critères : FEAT-006-AC03

- **Étant donné** une passerelle qui répond 500 à chaque requête, puis une passerelle injoignable
- **Quand** un code est envoyé
- **Alors** l'envoi échoue avec le statut 503 et le code `OTP_DELIVERY_FAILED`, après exactement 2 tentatives

### SPEC-006-01-SC05 — une erreur client n'est pas réessayée

Critères : FEAT-006-AC03

- **Étant donné** une passerelle qui répond 400
- **Quand** un code est envoyé
- **Alors** l'envoi échoue en 503 `OTP_DELIVERY_FAILED` après une seule requête

### SPEC-006-01-SC06 — le code n'est jamais journalisé

Critères : FEAT-006-AC03

- **Étant donné** un envoi réussi puis un envoi en échec
- **Quand** on capture tous les journaux de l'adaptateur
- **Alors** aucun ne contient le code, la clé ou le numéro complet

## Erreurs et cas limites

Passerelle lente : la requête est interrompue au bout de 5 s, puis un nouvel essai
a lieu. Une ligne `otp_codes` est déjà créée avant l'envoi : en cas d'échec, elle
reste sans usage et expire seule (comportement existant).

## Contrats API et données

- Variables d'environnement **nouvelles** : `SMS_HTTP_URL`, `SMS_HTTP_API_KEY`, `SMS_SENDER_ID`.
- Erreur HTTP **nouvelle** : 503 `OTP_DELIVERY_FAILED` sur `POST /v1/auth/otp/request`.
- `OtpDeliveryPort` inchangé.
