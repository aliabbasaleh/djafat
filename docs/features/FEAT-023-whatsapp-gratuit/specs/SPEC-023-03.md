# SPEC-023-03 — L'écran qui a affiché le code attend, puis se connecte

## Comportement observable

L'écran qui a reçu le code (SPEC-023-01) demande régulièrement où en est son code, avec son jeton.
Tant que le message n'est pas arrivé, il attend. Quand il est arrivé (SPEC-023-02), l'écran reçoit
l'issue une fois : la session (connexion, nouvel appareil), « numéro confirmé » (confirmation),
« numéro confirmé sur aucun compte » avec le numéro qui a écrit, ou « autre numéro ». Seul cet
écran peut l'apprendre : il faut le jeton, que rien d'autre ne connaît.

Aujourd'hui, le client recopie le code reçu en réponse (`POST /auth/whatsapp/verify`,
`auth.controller.ts:47-58`) ; rien ne lie le code à un écran.

## Règles métier

- R1 — Un jeton inconnu, un code expiré sans message ou un code déjà rendu donnent la même réponse :
  « expiré ». Un message arrivé se lit peu après, jamais des heures plus tard : passé 10 minutes
  après la fin de validité du code, « expiré » aussi _(v2, 2026-11-28, revue n° 3)_.
- R2 — Message pas encore arrivé, code valable : « en attente », avec la fin de validité.
- R3 — Chaque issue n'est rendue qu'une fois ; la demande suivante dit « expiré ».
- R4 — **Connexion**, compte à ouvrir : la session s'ouvre par le chemin commun
  (`AuthService.openSession` : compte actif sinon 403 `ACCOUNT_INACTIVE`, journal
  `AUTH_LOGIN_SUCCESS`) ; le numéro devient confirmé s'il ne l'était pas (le message le prouve,
  comme un code SMS) ; l'e-mail « Nouvelle connexion par WhatsApp » part (SPEC-023-04). Comme pour
  un code par e-mail, l'appareil n'est pas mémorisé.
- R5 — **Nouvel appareil**, compte à ouvrir : la connexion par mot de passe en attente est
  consommée (une seule fois ; expirée ou déjà utilisée → « expiré ») ; la session s'ouvre ;
  l'appareil est mémorisé si l'écran le demande (`rememberDevice`, SPEC-020-04 R9) ; l'e-mail
  part.
- R6 — **Confirmation** : « numéro confirmé » (le numéro l'est depuis l'arrivée du message ; il est
  confirmé de nouveau, sans effet s'il l'est déjà, avant de le dire — revue n° 2, v2, 2026-11-28).
- R7 — « Numéro confirmé sur aucun compte » : avec le numéro qui a écrit (E.164), pour remplir
  « Créer un compte ».
- R8 — « Autre numéro » : sans autre détail.

## Scénarios

### SPEC-023-03-SC01 — en attente, puis connecté une seule fois

Critères : FEAT-023-AC02

- **Étant donné** un code de connexion demandé par un écran
- **Quand** l'écran demande avant le message, puis après l'issue « compte à ouvrir », puis encore
- **Alors** il reçoit « en attente » avec la fin de validité, puis la session (jetons et compte, le
  numéro désormais confirmé), puis « expiré » ; une seule session a été ouverte.

### SPEC-023-03-SC02 — un autre jeton n'apprend rien

Critères : FEAT-023-AC02

- **Étant donné** un code arrivé, issue « compte à ouvrir »
- **Quand** on demande avec un jeton inventé
- **Alors** « expiré » ; aucune session n'est ouverte ; le bon jeton reçoit toujours la session.

### SPEC-023-03-SC03 — numéro confirmé sur aucun compte : le numéro, rien d'autre

Critères : FEAT-023-AC03

- **Étant donné** l'issue « numéro confirmé sur aucun compte » depuis `+33612345678`
- **Quand** l'écran demande
- **Alors** il reçoit cette issue avec `+33612345678`, sans session ; la demande suivante dit
  « expiré ».

### SPEC-023-03-SC04 — nouvel appareil : session et appareil mémorisé

Critères : FEAT-023-AC02

- **Étant donné** un code de nouvel appareil arrivé depuis le numéro confirmé du compte
- **Quand** l'écran demande avec « se souvenir de cet appareil »
- **Alors** la session s'ouvre avec un jeton d'appareil ; la connexion par mot de passe est
  consommée ; si elle avait expiré entre-temps, « expiré » et pas de session.

### SPEC-023-03-SC05 — confirmation : numéro confirmé

Critères : FEAT-023-AC05

- **Étant donné** un code de confirmation arrivé depuis le numéro du compte
- **Quand** l'écran demande
- **Alors** « numéro confirmé » ; le profil du compte dit son numéro confirmé.

### SPEC-023-03-SC06 — compte suspendu : refusé, pas de session

Critères : FEAT-023-AC02

- **Étant donné** l'issue « compte à ouvrir » pour un compte suspendu depuis
- **Quand** l'écran demande
- **Alors** 403 `ACCOUNT_INACTIVE`, pas de session ; la demande suivante dit « expiré ».

### SPEC-023-03-SC07 — code expiré sans message

Critères : FEAT-023-AC02

- **Étant donné** un code dont la validité est passée sans message
- **Quand** l'écran demande
- **Alors** « expiré ».

### SPEC-023-03-SC08 — un message arrivé ne se lit pas des heures plus tard

Critères : FEAT-023-AC02

- **Étant donné** un code de connexion arrivé à 10 h 00 (valable 5 min)
- **Quand** l'écran demande pour la première fois à 10 h 15 et 1 s
- **Alors** « expiré », et aucune session n'est ouverte _(v2, 2026-11-28, revue n° 3)_

## Erreurs et cas limites

- 403 `ACCOUNT_INACTIVE` (R4, R5) ; 422 `VALIDATION_ERROR` pour un corps mal formé.
- Deux demandes simultanées après l'arrivée : une seule reçoit l'issue (R3, mise à jour
  conditionnelle), l'autre « expiré ».
- La réponse se perd en chemin : l'issue est déjà rendue (R3) ; l'écran redemande un code.

## Contrats API et données

- _nouveau_ `POST /v1/auth/whatsapp/status` (public, 200), corps `WhatsappStatusSchema`
  `{ token: string, rememberDevice?: boolean }` (strict).
- Réponses : `{ status: 'waiting', expiresAt }` · `{ status: 'expired' }` ·
  `{ status: 'signed_in', access, accessExpiresAt, refresh, refreshExpiresAt, user, deviceToken?,
deviceTokenExpiresAt? }` · `{ status: 'not_confirmed', phone }` · `{ status: 'wrong_number' }` ·
  `{ status: 'confirmed' }`.
- Table `whatsapp_codes` : `consumed_at` (SPEC-023-01).
- _retiré_ `POST /v1/auth/whatsapp/verify` (FEAT-008, jamais en service) ; `POST /me/phone/verify`
  et `POST /auth/password/challenge/verify` n'acceptent plus le canal `whatsapp` (SPEC-023-08).

## Autorisations

Public : le jeton (256 bits, connu du seul écran) est la preuve. Il ne donne qu'une issue, une
fois ; la session s'ouvre pour le compte du numéro qui a écrit, jamais pour un compte choisi par
l'écran.

## Hypothèses et questions ouvertes

- Issue rendue une fois, jeton inconnu = expiré (FEAT-023-Q10).
- Pas de limite par réseau sur cette route : le jeton ne se devine pas, et beaucoup de clients
  partagent une adresse au Tchad (FEAT-023-Q11).
