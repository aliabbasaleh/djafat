# SPEC-023-01 — Le code à envoyer sur WhatsApp

## Comportement observable

Un écran demande un code à envoyer. L'API répond avec le code, le message déjà écrit qui le
contient, le lien qui ouvre WhatsApp sur le numéro de DJAFAT avec ce message, ce numéro, la fin de
validité, et un jeton que seul cet écran connaît (il s'en sert pour attendre, SPEC-023-03). DJAFAT
n'envoie rien : c'est le client qui enverra le message.

Trois usages, une seule forme de réponse :

- **connexion** (`login`) — « WhatsApp » dans « ou recevoir un code », sans compte connu ;
- **nouvel appareil** (`login_device`) — le code d'une connexion par mot de passe en attente
  (SPEC-020-04), à la place du code par e-mail ;
- **confirmation du numéro** (`verify_phone`) — un compte connecté confirme son propre numéro
  (SPEC-023-06).

Aujourd'hui, rien de tout cela : le client écrit « Code DJAFAT » et DJAFAT lui répond par un code
(`apps/api/src/modules/auth/whatsapp-inbound.service.ts:105-133`), message payant ; le lien
`wa.me` porte un texte fixe (`auth-methods.ts:18`, `WHATSAPP_LOGIN_TEXT`).

## Règles métier

- R1 — Seulement si WhatsApp est en service sur ce déploiement (`GET /auth/methods`, entrée
  `whatsapp` disponible : `WHATSAPP_BUSINESS_NUMBER` renseigné, et `WHATSAPP_PROVIDER=cloud` ou le
  faux hors production, `auth-methods.ts:40-53`) ; sinon 503 `WHATSAPP_UNAVAILABLE`, rien n'est
  créé. Les écrans montrent alors « Bientôt disponible » (FEAT-020, inchangé) : WhatsApp s'allume
  quand ses réglages sont remplis, sans changer le code.
- R2 — Le code : 6 chiffres tirés au hasard (`generateOtpCode`), différent de tout autre code qui
  attend encore son message ; valable `otp_ttl_seconds` (5 min par défaut), jamais plus longtemps
  que la connexion par mot de passe qu'il termine (10 min, SPEC-020-04).
- R3 — Le message déjà écrit :
  - connexion et nouvel appareil : « Je me connecte à DJAFAT : 482915 (n'envoyez ce code que pour
    vous connecter vous-même) » ;
  - confirmation du numéro : « Je confirme mon numéro sur DJAFAT : 482915 (n'envoyez ce code que
    pour votre propre compte) ».
- R4 — Le lien : `https://wa.me/<chiffres de WHATSAPP_BUSINESS_NUMBER>?text=<message encodé>` ; le
  numéro rendu est `WHATSAPP_BUSINESS_NUMBER` (E.164), pour l'envoyer depuis un autre appareil.
- R5 — Rien de secret n'est gardé en clair : le jeton (32 octets aléatoires) et le code ne sont
  stockés que sous forme d'empreinte HMAC (`OTP_HASH_SECRET`), comme les codes à usage unique.
- R6 — Budgets : chaque demande compte dans le budget du réseau (`otp_rate_limit_per_ip`, 429
  `RATE_LIMITED`). Nouvel appareil et confirmation comptent aussi dans celui du numéro du compte
  (`otp_rate_limit_per_phone`) et respectent son verrou (423 `OTP_LOCKED`).
- R7 — Nouvel appareil : une connexion par mot de passe en attente (`challengeId`), sinon 401
  `OTP_INVALID` ; le numéro du compte doit être confirmé, sinon 409 `PHONE_NOT_CONFIRMED` (même
  réponse que le code par SMS, `password.service.ts:146-158`).
- R8 — Confirmation : compte connecté ; numéro déjà confirmé → 409 `PHONE_ALREADY_CONFIRMED`.
- R9 — Les codes expirés sont effacés quand un nouveau est créé ; la demande est journalisée
  (`AUTH_OTP_REQUESTED`, canal `whatsapp`, usage), sans code ni jeton.

## Scénarios

### SPEC-023-01-SC01 — connexion : code, message avec l'avertissement, lien, jeton

Critères : FEAT-023-AC01, FEAT-023-AC08

- **Étant donné** WhatsApp en service, numéro de DJAFAT `+23566868973`
- **Quand** un écran demande un code de connexion
- **Alors** la réponse donne un code de 6 chiffres, le message « Je me connecte à DJAFAT : <code>
  (n'envoyez ce code que pour vous connecter vous-même) », le lien `https://wa.me/23566868973?text=`
  suivi de ce message encodé, le numéro `+23566868973`, une fin de validité 5 min plus tard et un
  jeton ; la base ne garde ni le code ni le jeton en clair.

### SPEC-023-01-SC02 — WhatsApp éteint : refusé, rien n'est créé

Critères : FEAT-023-AC06

- **Étant donné** `WHATSAPP_BUSINESS_NUMBER` absent (ou le faux WhatsApp en production)
- **Quand** un écran demande un code
- **Alors** 503 `WHATSAPP_UNAVAILABLE` ; aucun code n'est créé ; `GET /auth/methods` dit WhatsApp
  indisponible.

### SPEC-023-01-SC03 — deux codes en attente ne sont jamais égaux

Critères : FEAT-023-AC01

- **Étant donné** un code qui attend son message
- **Quand** le tirage suivant donne le même code
- **Alors** un autre code est tiré ; les deux codes rendus diffèrent.

### SPEC-023-01-SC04 — nouvel appareil : message de connexion, durée bornée par la connexion

Critères : FEAT-023-AC01, FEAT-023-AC08

- **Étant donné** une connexion par mot de passe en attente, au numéro de compte confirmé, qui
  expire dans 2 minutes
- **Quand** l'écran demande un code WhatsApp pour elle
- **Alors** le message est celui de la connexion, la fin de validité est celle de la connexion en
  attente ; une connexion inconnue ou expirée donne 401 `OTP_INVALID`, un numéro non confirmé
  409 `PHONE_NOT_CONFIRMED`.

### SPEC-023-01-SC05 — confirmation : message de confirmation ; numéro déjà confirmé refusé

Critères : FEAT-023-AC01, FEAT-023-AC08

- **Étant donné** un compte connecté au numéro non confirmé
- **Quand** il demande un code pour confirmer son numéro
- **Alors** le message est « Je confirme mon numéro sur DJAFAT : <code> (n'envoyez ce code que pour
  votre propre compte) » ; le même compte, numéro confirmé, reçoit 409 `PHONE_ALREADY_CONFIRMED`.

### SPEC-023-01-SC06 — trop de demandes depuis un réseau : 429

Critères : FEAT-023-AC01

- **Étant donné** le budget du réseau épuisé
- **Quand** un écran demande un code
- **Alors** 429 `RATE_LIMITED` ; aucun code n'est créé.

## Erreurs et cas limites

- 503 `WHATSAPP_UNAVAILABLE` « WhatsApp n'est pas disponible pour le moment. » (R1).
- 429 `RATE_LIMITED`, 423 `OTP_LOCKED` (R6) ; 401 `OTP_INVALID`, 409 `PHONE_NOT_CONFIRMED` (R7) ;
  409 `PHONE_ALREADY_CONFIRMED` « Votre numéro est déjà confirmé. » (R8).
- Tirage : au plus 5 essais contre un code déjà en attente (index unique), puis 503
  `WHATSAPP_UNAVAILABLE` — en pratique jamais (un million de codes).

## Contrats API et données

- _nouveau_ `POST /v1/auth/whatsapp/start` (public), corps `WhatsappStartSchema`
  `{ challengeId?: uuid }` (strict) : sans `challengeId` connexion, avec nouvel appareil.
- _nouveau_ `POST /v1/me/phone/whatsapp` (connecté), corps `{}` (strict) : confirmation.
- Réponse 201 (les deux) : `{ token, code, text, link, number, expiresAt }`.
- _nouveau_ table `whatsapp_codes` (migration `0042_whatsapp_codes`) : `id`, `purpose`
  (`login` | `login_device` | `verify_phone`), `code_hash`, `token_hash` (unique), `user_id`
  (compte, sauf connexion), `challenge_id` (nouvel appareil), `sender_phone`, `outcome`,
  `matched_user_id`, `received_at`, `consumed_at`, `expires_at`, `created_at` ; index unique sur
  `code_hash` tant que le message n'est pas arrivé.
- `GET /v1/auth/methods` : l'entrée `whatsapp` perd `link` (le lien porte désormais le code) ;
  idem pour la liste `channels` d'une connexion par mot de passe (`CodeChannelDto`).

## Autorisations

Connexion et nouvel appareil : public (comme `POST /auth/otp/request`) ; le nouvel appareil exige
une connexion par mot de passe en attente. Confirmation : `@RequireAuth()`, le compte vient du
jeton d'accès, jamais du corps.
