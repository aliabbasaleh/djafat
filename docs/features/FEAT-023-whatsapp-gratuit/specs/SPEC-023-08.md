# SPEC-023-08 — Plus de réponse payante, et le guide pour relier le numéro à Meta

## Comportement observable

DJAFAT n'envoie plus aucun code par WhatsApp : la réponse de FEAT-008, facturée par Meta depuis le
1er octobre 2026, disparaît avec tout ce qui ne servait qu'à elle. WhatsApp reste éteint tant que
ses réglages manquent, et s'allume quand ils sont remplis. Un guide dit comment relier le numéro
de DJAFAT à l'API WhatsApp Cloud et ce que change chacun des deux choix de numéro. Sur un poste de
développement, un script simule le message d'un client.

Aujourd'hui : transport `whatsapp` de `OtpDeliveryPort` (`providers/cloud-whatsapp-otp-delivery.provider.ts`,
faux `mock-whatsapp-otp-delivery.provider.ts`, texte `whatsapp-otp-text.ts`, branchés dans
`auth.module.ts`), route `POST /auth/whatsapp/verify`, plafond `WHATSAPP_MAX_CODES_PER_HOUR`
(`packages/config/src/env.ts`, `.env.example`) ; `docs/39-comptes-externes.md` §3 ne fait que citer
WhatsApp Business.

## Règles métier

- R1 — Plus aucun code ne part par WhatsApp : le transport `whatsapp` (réel et faux), son texte,
  `POST /auth/whatsapp/verify`, le canal `whatsapp` de `POST /me/phone/verify` et de
  `POST /auth/password/challenge/verify`, et `WHATSAPP_MAX_CODES_PER_HOUR` sont retirés. Un
  message « Code DJAFAT » ne donne rien (SPEC-023-02 R3).
- R2 — Inchangé : WhatsApp est en service avec `WHATSAPP_BUSINESS_NUMBER` et
  `WHATSAPP_PROVIDER=cloud` (ou le faux hors production) ; en production, `cloud` exige ses cinq
  réglages (`env.ts`, SPEC-008-01). Les réponses aux commandes par WhatsApp (FEAT-017,
  `WhatsappTextReplyService`) ne changent pas.
- R3 — Le guide (`docs/39-comptes-externes.md`, nouvelle section « WhatsApp pour les connexions »)
  dit : ce qu'il faut (compte Meta Business, un numéro WhatsApp, une application Meta avec le
  produit WhatsApp) ; l'adresse du webhook `https://api.<domaine>/v1/auth/whatsapp/webhook`, le
  jeton de vérification et l'abonnement au champ `messages` ; les réglages de `.env.prod` ; les
  deux choix de numéro — un second numéro pour les connexions seulement (les commandes restent sur
  le 66 86 89 73 dans l'application WhatsApp Business), ou le numéro des commandes (il quitte
  l'application WhatsApp Business, sauf « coexistence » si Meta la propose au Tchad, et chaque
  réponse à une commande par WhatsApp devient un message payant) ; comment vérifier (une connexion
  depuis un téléphone ; aucun message envoyé par DJAFAT pour les connexions dans la facturation
  Meta).
- R4 — Script de développement `scripts/dev/whatsapp-message.mjs` : envoie à l'API locale le
  message d'un client (`--from`, `--text`), signé avec `WHATSAPP_APP_SECRET` comme Meta ; refuse
  une adresse d'API qui n'est pas locale. `docs/TRAVAILLER-EN-LOCAL.md` dit comment s'en servir.

## Scénarios

### SPEC-023-08-SC01 — aucun code ne part par WhatsApp

Critères : FEAT-023-AC04

- **Étant donné** l'API avec WhatsApp en service
- **Quand** on se connecte, confirme un numéro ou passe un nouvel appareil par WhatsApp, et
  qu'arrive « Code DJAFAT »
- **Alors** aucun message WhatsApp n'est envoyé (ni par l'API Graph ni dans la boîte du faux) ;
  `POST /auth/whatsapp/verify` répond 404 ; `POST /me/phone/verify` et
  `POST /auth/password/challenge/verify` refusent le canal `whatsapp` (422).

### SPEC-023-08-SC02 — réglages : WhatsApp s'allume sans changer le code

Critères : FEAT-023-AC06

- **Étant donné** une configuration de production sans réglages WhatsApp, puis avec
  `WHATSAPP_PROVIDER=cloud` et ses cinq réglages
- **Quand** l'API lit sa configuration et `GET /auth/methods` répond
- **Alors** WhatsApp indisponible, puis disponible ; `cloud` sans un de ses réglages est refusé au
  démarrage ; `WHATSAPP_MAX_CODES_PER_HOUR` n'existe plus.

### SPEC-023-08-SC03 — le guide [evidence: review]

Critères : FEAT-023-AC07

- **Étant donné** `docs/39-comptes-externes.md`
- **Quand** on le lit
- **Alors** il donne tout ce que dit R3, sans secret ni identifiant réel.

### SPEC-023-08-SC04 — le script de développement [evidence: manual]

Critères : FEAT-023-AC04

- **Étant donné** l'API locale avec `WHATSAPP_APP_SECRET` et `WHATSAPP_PHONE_NUMBER_ID`
- **Quand** le script envoie le message d'un client qui porte un code affiché par un écran
- **Alors** l'API l'accepte comme un message de Meta (200) et l'écran se connecte — c'est ce qui
  mène les captures de SPEC-023-05 à 07 ; une adresse d'API non locale est refusée sans rien
  envoyer.

## Erreurs et cas limites

- Un ancien client qui appelle `POST /auth/whatsapp/verify` : 404 (jamais en service, aucune
  version publiée ne s'en sert).
- `WHATSAPP_MAX_CODES_PER_HOUR` encore dans un `.env` : ignoré (variable inconnue).

## Contrats API et données

Retraits listés en R1. `packages/config/src/env.ts` : `WHATSAPP_MAX_CODES_PER_HOUR` retiré ;
les autres variables `WHATSAPP_*` inchangées. `.env.example` mis à jour. La contrainte de canal de
`otp_codes` garde `whatsapp` (aucune migration de données : d'anciennes lignes peuvent exister).
