# SPEC-020-03 — Créer un compte, confirmé par un code e-mail

## Comportement observable

Aujourd'hui un compte ne naît que d'une connexion par code SMS ou WhatsApp : `findOrCreateByPhone`
le crée avec le seul téléphone (`apps/api/src/modules/users/users.service.ts:84-103`). Le but de
code `register` est déclaré (`otp.service.ts:24`, contrainte `otp_codes_purpose_check` de
`prisma/migrations/0030_email_otp/migration.sql:15-16`) mais aucune route ne s'en sert.

Après la spec, trois routes publiques (_nouvelles_) :

- `POST /v1/auth/register { fullName, phone, email, password }` → 202 `{ registrationId, expiresAt }` ;
- `POST /v1/auth/register/verify { registrationId, code }` → 200, la même réponse que
  `POST /v1/auth/otp/verify` (`access`, `refresh`, `user`…) plus `deviceToken` et
  `deviceTokenExpiresAt` ;
- `POST /v1/auth/register/resend { registrationId }` → 202.

Rien n'est écrit dans `users` avant le bon code.

## Règles métier

- R1 — Champs : `fullName` de 2 à 80 caractères (espaces resserrés), `phone` saisi à la tchadienne et ramené en E.164 (FEAT-005), `email` normalisé (`EmailInputSchema`), `password` soumis à SPEC-020-02 avec le contexte e-mail, téléphone et nom. La confirmation du mot de passe est vérifiée par l'écran, pas par l'API.
- R2 — Un numéro porté par un compte non supprimé : 409 `PHONE_ALREADY_USED` (_nouveau_), « Ce numéro a déjà un compte. Connectez-vous avec ce numéro ou avec l'e-mail de ce compte. » Rien n'est envoyé ni enregistré (FEAT-020-Q06).
- R3 — Une adresse portée par un compte non supprimé : réponse 202 de même forme ; une inscription **leurre** est enregistrée, sans nom, numéro ni mot de passe, et sans code : elle ne peut jamais aboutir ; l'avis « vous avez déjà un compte » (SPEC-020-01) part à cette adresse, dans le même budget d'envoi qu'un code. _(v2, revue n° 3)_
- R4 — Sinon, une inscription en attente est enregistrée (`auth_challenges`, genre `registration`, valable 30 minutes) avec le nom, le téléphone et le **hachage** du mot de passe, et un code `register` **lié à cette inscription** part à l'adresse.
- R5 — Le bon code de **cette** inscription crée, dans une transaction : le compte (`status` actif, `email` et `email_verified_at`, `phone` sans `phone_verified_at`, `full_name`, `password_hash`, `password_updated_at`), son rôle `customer`, et marque l'inscription consommée. La session s'ouvre par le chemin commun (`AuthService.openSession`, `auth.service.ts:142-186`), l'appareil est mémorisé (SPEC-020-04 R9) et l'audit `AUTH_REGISTERED` (_nouveau_) est écrit.
- R6 — Un mauvais code, une inscription expirée, consommée ou inconnue : 401 `OTP_INVALID`, sans distinction. Les essais, l'expiration et le verrou sont ceux de tous les codes (`otp.service.ts:150-207`).
- R7 — Un code ne vaut que pour l'inscription qui l'a demandé : deux inscriptions en attente pour la même adresse ne peuvent pas se compléter l'une l'autre.
- R8 — Si le numéro ou l'adresse a été pris entre la demande et le code : 409 `PHONE_ALREADY_USED` ou `EMAIL_ALREADY_USED`, aucun compte créé.
- R9 — `resend` envoie un nouveau code pour la même inscription ; seul le dernier code est valable. Une inscription inconnue ou expirée répond 202 sans rien envoyer.
- R10 — Les demandes d'inscription consomment le budget par réseau des codes (`otp_rate_limit_per_ip`), y compris quand elles finissent en 409, ce qui freine le sondage des numéros.
- R11 — Chaque nouvelle inscription en attente supprime d'abord les lignes expirées de `auth_challenges` (FEAT-020-Q15).
- R12 — Après l'inscription, l'adresse est vérifiée : la connexion par code e-mail de FEAT-007 (`auth.service.ts:104-120`) fonctionne pour ce compte.
- R13 — Rien ne distingue une adresse prise d'une libre _(v2, revue n° 3)_ : le verrou est vérifié avant tout (423 `OTP_LOCKED` pour les deux), le mot de passe est haché et une inscription en attente enregistrée dans les deux cas, `resend` et `verify` suivent le même chemin (une inscription leurre n'a pas de code : un essai y compte comme un mauvais code, verrou après 10), et un e-mail qui ne peut pas partir donne le même 503 (`OTP_DELIVERY_FAILED` ou `EMAIL_UNAVAILABLE`).
- R14 — Connexion par code e-mail (FEAT-007, AC08) _(v2, revue n° 4)_ : même budget par adresse et même verrou pour toute adresse ; le code ne part que pour une adresse vérifiée, en arrière-plan, et un échec d'envoi est journalisé sans changer la réponse.

## Scénarios

### SPEC-020-03-SC01 — demande d'inscription : inscription en attente et code lié

Critères : FEAT-020-AC03

- **Étant donné** aucune donnée pour `+23566123456` ni `awa@example.td`
- **Quand** l'inscription est demandée avec nom, téléphone « 66 12 34 56 », e-mail « Awa@Example.td » et un mot de passe valable
- **Alors** la réponse est 202 avec un `registrationId` ; l'inscription en attente garde un hachage scrypt (jamais le mot de passe) ; un code `register` lié à cette inscription est demandé pour `awa@example.td`

### SPEC-020-03-SC02 — bon code : compte créé, session ouverte, appareil mémorisé

Critères : FEAT-020-AC03, FEAT-020-AC15

- **Étant donné** l'inscription de SC01 et son code
- **Quand** le code est vérifié
- **Alors** un compte client existe avec l'e-mail vérifié, le téléphone non vérifié, un mot de passe ; la réponse contient les jetons, le `user` et un `deviceToken` ; l'audit `AUTH_REGISTERED` est écrit sans e-mail ni téléphone en clair

### SPEC-020-03-SC03 — mauvais code : rien n'est créé

Critères : FEAT-020-AC03

- **Étant donné** l'inscription de SC01
- **Quand** un mauvais code est vérifié
- **Alors** la réponse est 401 `OTP_INVALID` et aucun compte n'existe

### SPEC-020-03-SC04 — adresse déjà inscrite : même réponse, avis au lieu du code

Critères : FEAT-020-AC04

- **Étant donné** un compte pour `awa@example.td`
- **Quand** une inscription est demandée avec cette adresse et un autre numéro
- **Alors** la réponse est 202 de même forme ; une inscription leurre est enregistrée, sans nom, numéro ni mot de passe ; aucun code n'est demandé ; l'avis « vous avez déjà un compte » part à `awa@example.td` ; vérifier un code pour ce `registrationId` répond 401 `OTP_INVALID`

### SPEC-020-03-SC05 — numéro déjà utilisé : refus

Critères : FEAT-020-AC04, FEAT-020-AC02

- **Étant donné** un compte pour `+23566123456`
- **Quand** une inscription est demandée avec « 66 12 34 56 »
- **Alors** la réponse est 409 `PHONE_ALREADY_USED` ; rien n'est envoyé ni enregistré

### SPEC-020-03-SC06 — un code ne complète que son inscription

Critères : FEAT-020-AC03

- **Étant donné** deux inscriptions en attente A et B pour `awa@example.td`, chacune avec son code
- **Quand** le code de A est vérifié pour B, puis le code de B pour B, puis le code de A pour A
- **Alors** le premier est refusé (`OTP_INVALID`), le second crée le compte, le troisième répond 409 `EMAIL_ALREADY_USED`

### SPEC-020-03-SC07 — inscription expirée

Critères : FEAT-020-AC03

- **Étant donné** une inscription en attente créée il y a plus de 30 minutes
- **Quand** son code est vérifié
- **Alors** la réponse est 401 `OTP_INVALID` et aucun compte n'est créé

### SPEC-020-03-SC08 — renvoyer le code

Critères : FEAT-020-AC03

- **Étant donné** l'inscription de SC01
- **Quand** `resend` est appelé, puis l'ancien code et le nouveau sont vérifiés
- **Alors** un nouveau code lié est demandé ; l'ancien est refusé, le nouveau crée le compte ; `resend` sur un identifiant inconnu répond 202 sans envoi

### SPEC-020-03-SC09 — champs invalides

Critères : FEAT-020-AC02

- **Étant donné** un nom vide, un numéro « 12 », une adresse « awa@ », un mot de passe « 1234 »
- **Quand** le schéma d'inscription les valide
- **Alors** il échoue sur `fullName`, `phone`, `email` et `password`, chacun avec un message français

### SPEC-020-03-SC10 — de bout en bout sur PostgreSQL

Critères : FEAT-020-AC03, FEAT-020-AC08

- **Étant donné** l'API sur PostgreSQL et Redis réels, avec le faux envoi d'e-mails
- **Quand** une inscription est demandée puis vérifiée avec le code lu dans Redis, puis une connexion par code e-mail est demandée et vérifiée
- **Alors** `GET /v1/me` montre `emailVerified: true`, `phoneVerified: false`, `hasPassword: true`, et la connexion par code e-mail ouvre le même compte

### SPEC-020-03-SC11 — adresses verrouillées : même 423

Critères : FEAT-020-AC04

- **Étant donné** une adresse prise et une adresse libre, toutes deux verrouillées (10 échecs)
- **Quand** une inscription est demandée avec chacune
- **Alors** les deux répondent 423 `OTP_LOCKED` ; rien n'est enregistré ni envoyé

### SPEC-020-03-SC12 — même budget, y compris par `resend`

Critères : FEAT-020-AC04

- **Étant donné** une adresse prise et une adresse libre
- **Quand** pour chacune on demande l'inscription puis deux fois `resend`, puis une troisième
- **Alors** les deux premiers renvois passent et le troisième répond 429 `RATE_LIMITED`, pour les deux

### SPEC-020-03-SC13 — mêmes échecs et même 503

Critères : FEAT-020-AC04

- **Étant donné** une inscription réelle et une inscription leurre
- **Quand** dix mauvais codes sont essayés sur chacune ; puis, pour l'adresse prise, l'avis ne peut pas partir
- **Alors** les deux répondent 401 dix fois puis 423 ; l'avis manqué répond 503 `OTP_DELIVERY_FAILED` (ou `EMAIL_UNAVAILABLE` sur un déploiement sans e-mail), comme un code manqué

### SPEC-020-03-SC14 — code de connexion : même chemin pour toute adresse

Critères : FEAT-020-AC08

- **Étant donné** une adresse vérifiée et une adresse inconnue
- **Quand** un code de connexion est demandé pour chacune
- **Alors** les deux dépensent le même budget et rencontrent le même verrou ; seule l'adresse vérifiée reçoit un code, envoyé en arrière-plan ; un envoi qui échoue est journalisé, sans l'adresse, et ne change pas la réponse

## Erreurs et cas limites

- 422 `VALIDATION_ERROR` (chemins `fullName`, `phone`, `email`, `password`), 409
  `PHONE_ALREADY_USED`, 409 `EMAIL_ALREADY_USED` (course, R8), 401 `OTP_INVALID`, 423
  `OTP_LOCKED`, 429 `RATE_LIMITED`, 503 `OTP_DELIVERY_FAILED` ou `EMAIL_UNAVAILABLE`.
- Une adresse saisie avec majuscules ou espaces est la même adresse (citext + normalisation).
- Un compte supprimé (anonymisé) ne bloque ni son ancien numéro ni son ancienne adresse
  (index partiels `WHERE deleted_at IS NULL`).

## Contrats API et données

- Routes _nouvelles_ ci-dessus ; schémas `dto/register.schema.ts` (_nouveau_).
- Code d'erreur `PHONE_ALREADY_USED` (_nouveau_) dans `API_ERROR_CODES` (`packages/types/src/errors.ts`).
- Audit `AUTH_REGISTERED` (_nouveau_) dans `AuditAction` (`common/audit/audit.service.ts:11-49`).
- `MeDto` gagne `phoneVerified` et `hasPassword` (_nouveaux_, additifs).
- Migration `0040_customer_accounts` (_nouvelle_) : `users.password_hash`, `users.password_updated_at` ;
  table `auth_challenges` ; `otp_codes.context` ; buts `login_device`, `reset_password`,
  `verify_phone` ajoutés à `otp_codes_purpose_check` ; table `trusted_devices` (SPEC-020-04).
- `OtpService.requestCode` / `verifyCode` acceptent une liaison facultative (`context`) ; sans elle,
  le comportement actuel est inchangé.

## Autorisations

Routes publiques, limitées en débit. Le compte créé reçoit le seul rôle `customer`.

## Hypothèses et questions ouvertes

- Technique : l'avis « déjà un compte » remplace le code pour ne pas révéler l'adresse (FEAT-007-Q05,
  même principe). Le refus d'un numéro déjà utilisé, lui, est visible : choix de l'utilisateur
  (FEAT-020-Q06).
- Technique : la liaison code ↔ inscription réalise le durcissement prévu par FEAT-007-Q07.
