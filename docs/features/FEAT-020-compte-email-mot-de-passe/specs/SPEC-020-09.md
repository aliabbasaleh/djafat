# SPEC-020-09 — « Mon profil » du site : mot de passe et numéro de téléphone

## Comportement observable

Aujourd'hui « Mon profil » (`apps/web/src/app/profil/page.tsx:136-218`) montre le nom (modifiable),
l'e-mail (ajout et vérification, FEAT-007) et « Se déconnecter ». Rien sur le mot de passe ni sur
le numéro.

Après la spec, deux sections de plus.

## Règles métier

- R1 — Section « Mot de passe », selon `MeDto` : `hasPassword` → « Changer le mot de passe » (Mot de passe actuel, Nouveau mot de passe, Confirmer) ; sans mot de passe mais `emailVerified` → « Définir un mot de passe » (Nouveau, Confirmer) ; sans e-mail vérifié → « Ajoutez votre e-mail ci-dessus pour pouvoir vous connecter avec un mot de passe. »
- R2 — Après un changement : message « Mot de passe modifié. Vos autres appareils ont été déconnectés. » ; `CURRENT_PASSWORD_INCORRECT` va sous « Mot de passe actuel », un 422 sous « Nouveau mot de passe ».
- R3 — Section « Téléphone » : le numéro et son état, « Confirmé ✓ » ou « Non confirmé ». Non confirmé : boutons « Confirmer par WhatsApp » et « Confirmer par SMS », chacun désactivé « Bientôt disponible » si `GET /auth/methods` le déclare indisponible ; puis le champ du code et « Vérifier ».
- R4 — Confirmer par WhatsApp : l'écran ouvre le lien `wa.me` (« Code DJAFAT ») et demande le code reçu en réponse ; par SMS : il demande l'envoi puis le code. _(v2, 2026-11-28 : par WhatsApp, remplacée par SPEC-023-06 R1 — FEAT-023 : l'écran affiche un code que le client envoie depuis son numéro, rien n'est tapé ; le SMS ne change pas.)_

## Scénarios

### SPEC-020-09-SC01 — section mot de passe selon le compte

Critères : FEAT-020-AC11

- **Étant donné** trois profils : avec mot de passe ; sans mot de passe avec e-mail vérifié ; sans e-mail vérifié
- **Quand** l'état de la section est calculé
- **Alors** il vaut « changer », « définir », puis « ajouter un e-mail d'abord »

### SPEC-020-09-SC02 — section téléphone selon le compte et les canaux

Critères : FEAT-020-AC12, FEAT-020-AC09

- **Étant donné** un numéro confirmé ; puis non confirmé avec WhatsApp et SMS indisponibles ; puis non confirmé avec SMS disponible
- **Quand** l'état de la section est calculé
- **Alors** « Confirmé ✓ » sans bouton ; puis deux boutons désactivés « Bientôt disponible » ; puis « Confirmer par SMS » actif

### SPEC-020-09-SC03 — changer et confirmer dans un navigateur [evidence: manual]

Critères : FEAT-020-AC11, FEAT-020-AC12

- **Étant donné** le site et l'API locaux (faux envois, SMS et WhatsApp disponibles en développement)
- **Quand** un client connecté change son mot de passe, puis confirme son numéro par SMS
- **Alors** les messages de R2 s'affichent, puis « Confirmé ✓ » ; captures dans `assets/exec-*`

## Erreurs et cas limites

- 409 `EMAIL_REQUIRED` (course : e-mail retiré entre-temps) : message de R1, troisième cas.
- 503 `SMS_UNAVAILABLE` : « Le SMS n'est pas disponible pour le moment. »

## Contrats API et données

Routes `PUT /v1/me/password` (SPEC-020-05), `POST /v1/me/phone/request` et `/verify`
(SPEC-020-06), par `@djafat/sdk` ; `MeProfile` gagne `phoneVerified` et `hasPassword`
(`packages/sdk/src/auth.ts:25-32`).
