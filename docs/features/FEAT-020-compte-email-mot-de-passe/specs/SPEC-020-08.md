# SPEC-020-08 — L'écran « Compte » de l'application mobile

## Comportement observable

Aujourd'hui l'application mobile déconnectée ouvre `app/(auth)/login.tsx` : un numéro, un code
SMS, rien d'autre (`apps/mobile/app/(auth)/login.tsx:18-132`). La session est gardée dans
SecureStore (`apps/mobile/lib/auth-storage.ts`, `lib/auth-context.tsx:24-80`).

Après la spec, le même écran devient « Mon compte », avec les deux onglets et les mêmes parcours
que le site (SPEC-020-07 R1 à R6), en composants natifs.

## Règles métier

- R1 — Mêmes éléments, même ordre et mêmes textes que SPEC-020-07 R1, R3, R5 et R6.
- R2 — Canaux : mêmes règles que SPEC-020-07 R2 ; WhatsApp ouvre le lien `wa.me` dans WhatsApp (`Linking`).
- R3 — Le `deviceToken` est gardé dans SecureStore et n'est pas effacé à la déconnexion.
- R4 — Une fois connecté : l'écran garde le comportement actuel (`redirect` interne `/(app)/…` suivi, sinon la liste des restaurants, `login.tsx:60-66`).
- R5 — Mêmes contrôles et mêmes messages d'erreur que SPEC-020-07 R4 et R8.

## Scénarios

### SPEC-020-08-SC01 — contrôles et traduction des erreurs

Critères : FEAT-020-AC02, FEAT-020-AC06

- **Étant donné** les cas de SPEC-020-07-SC03, SC04 et SC06
- **Quand** la logique cliente de l'application les traite
- **Alors** elle donne les mêmes champs et les mêmes messages que le site

### SPEC-020-08-SC02 — canaux actifs et « Bientôt disponible »

Critères : FEAT-020-AC09

- **Étant donné** les réponses de SPEC-020-07-SC05
- **Quand** les boutons de canal sont calculés
- **Alors** ils sont les mêmes que sur le site

### SPEC-020-08-SC03 — écran à deux onglets et parcours [evidence: manual]

Critères : FEAT-020-AC01, FEAT-020-AC03, FEAT-020-AC06, FEAT-020-AC10

- **Étant donné** l'application lancée en version web d'Expo contre l'API locale (l'application native ne s'installe pas encore sur un téléphone, constat MOB-01)
- **Quand** un visiteur crée un compte, se déconnecte et se reconnecte par mot de passe, puis réinitialise son mot de passe
- **Alors** l'écran montre « Mon compte » et ses deux onglets, et chaque parcours aboutit ; captures dans `assets/exec-*`

## Erreurs et cas limites

- SecureStore indisponible (web d'Expo) : le jeton d'appareil passe par la même solution de repli
  que la session (`lib/auth-storage.ts`).

## Contrats API et données

Aucun contrat nouveau : routes de SPEC-020-03 à SPEC-020-05 par `@djafat/sdk`.

## Autorisations

Écran public ; il n'apparaît que déconnecté (groupe `(auth)`).

## UI et accessibilité

Composants natifs du dépôt (`components/Button.tsx`, `components/Screen.tsx`, `TextInput`) ;
`accessibilityRole="tab"` et `accessibilityState.selected` sur les onglets ; `secureTextEntry`
pour les mots de passe ; `keyboardType` `email-address`, `phone-pad`, `number-pad` ;
`textContentType` `emailAddress`, `password`, `newPassword`, `oneTimeCode`.

## Références visuelles

FEAT-020-VIS01, FEAT-020-VIS02, FEAT-020-VIS03 : mêmes critères d'ordre et de présence que
SPEC-020-07 (SC03).

## Migrations

N/A — aucune.

## Hypothèses et questions ouvertes

- Hypothèse de périmètre (FEAT-020-Q09) : l'application mobile reçoit l'écran « Compte » ; les
  compléments du profil (mot de passe, numéro) restent sur le site, l'application n'ayant pas
  d'écran « Mon profil ».

## Stratégie de validation

Logique cliente pure dans `apps/mobile/lib/account.ts`, testée par vitest (SC01, SC02). Écran :
captures de la version web d'Expo (SC03), étape `/feature-visual`.

## Modules existants et points d'intégration

`app/(auth)/login.tsx` (présentation), `lib/auth-context.tsx`, `lib/auth-storage.ts`, `lib/api.ts`
(logique cliente), `@djafat/sdk`, `@djafat/core` (règle du mot de passe).
