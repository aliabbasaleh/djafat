# SPEC-020-06 — Confirmer son numéro ; codes WhatsApp ou SMS sur un compte créé par e-mail

## Comportement observable

Aujourd'hui, un bon code SMS ou WhatsApp trouve ou crée le compte du numéro, marque le numéro
vérifié et ouvre la session, quel que soit le compte (`auth.service.ts:61-72,130-139`,
`users.service.ts:84-103`). Après FEAT-020, un compte créé par e-mail porte un numéro **saisi**,
jamais prouvé : sans changement, la personne qui détient ce numéro (ou celui d'une faute de frappe)
entrerait dans le compte de quelqu'un d'autre. Le but `change_phone` existe mais ne sert à rien
(`otp.service.ts:24`).

Après la spec :

- `POST /v1/me/phone/request { channel: 'sms' }` → 202 (_nouveau_, connecté) ;
- `POST /v1/me/phone/verify { channel: 'sms', code }` → 200 `MeDto` (_nouveau_, connecté) ; _(v3, 2026-11-26 : `whatsapp` retiré, FEAT-023)_
- `POST /v1/auth/otp/verify` et `POST /v1/auth/whatsapp/verify` refusent un numéro non confirmé _(v3, 2026-11-26 : `/auth/whatsapp/verify` est retiré par FEAT-023 ; un message WhatsApp de ce numéro répond « numéro confirmé sur aucun compte », SPEC-023-02 R6.)_
  d'un compte créé par e-mail : 409 `PHONE_NOT_CONFIRMED`.

## Règles métier

- R1 — `request` par SMS : un code `verify_phone` **lié au compte** part au numéro du compte. SMS éteint : 503 `SMS_UNAVAILABLE` (inchangé). Numéro déjà confirmé : 202 sans envoi.
- R2 — Par WhatsApp, DJAFAT ne peut pas écrire le premier : le client envoie « Code DJAFAT » depuis son numéro (FEAT-008) et reçoit un code ; `verify` avec `channel: 'whatsapp'` accepte ce code pour le numéro du compte. _(v3, 2026-11-26 : remplacée par SPEC-023-06 — le client envoie depuis son numéro le code affiché, `POST /me/phone/whatsapp` ; rien n'est tapé.)_
- R3 — `verify` réussi : `phone_verified_at` est posé, `MeDto.phoneVerified` devient vrai, audit `AUTH_PHONE_VERIFIED` (_nouveau_). Mauvais code : 401 `OTP_INVALID` ; un code lié à un autre compte ne vaut pas.
- R4 — Connexion par code SMS ou WhatsApp : si le compte du numéro a un numéro **non confirmé** et une adresse vérifiée ou un mot de passe, la connexion est refusée en 409 `PHONE_NOT_CONFIRMED`, « Ce numéro est enregistré sur un compte créé avec un e-mail. Connectez-vous avec votre e-mail, puis confirmez votre numéro dans Mon profil. » Aucune session, numéro non marqué vérifié.
- R5 — Les autres comptes gardent le comportement actuel : comptes créés par code (numéro confirmé), comptes sans e-mail ni mot de passe (commandes par téléphone FEAT-011, données de démonstration).
- R6 — Une fois le numéro confirmé, les codes SMS et WhatsApp de ce numéro ouvrent ce compte. _(v3, 2026-11-26 : « codes WhatsApp » se lit « messages WhatsApp » depuis FEAT-023.)_
- R7 — Une commande prise au téléphone (FEAT-011) pour un numéro porté, **non confirmé**, par un compte qui a une adresse vérifiée ou un mot de passe : 409 `PHONE_NOT_CONFIRMED`, avec un message pour l'opérateur ; le numéro n'est pas confirmé et rien n'est enregistré. _(v2, revue n° 2, FEAT-020-Q27)_ Les commandes hors ligne par SMS ou WhatsApp ne confirment pas le numéro et restent inchangées (FEAT-020-Q31).

## Scénarios

### SPEC-020-06-SC01 — code de confirmation par SMS

Critères : FEAT-020-AC12

- **Étant donné** un compte créé par e-mail, au numéro `+23566123456` non confirmé, SMS actif
- **Quand** il demande la confirmation par SMS
- **Alors** un code `verify_phone` lié à ce compte part à `+23566123456`

### SPEC-020-06-SC02 — bon code SMS : numéro confirmé

Critères : FEAT-020-AC12

- **Étant donné** ce code
- **Quand** il est vérifié, puis un mauvais code sur un autre compte
- **Alors** `phoneVerified` devient vrai et `AUTH_PHONE_VERIFIED` est écrit ; le mauvais code répond 401 `OTP_INVALID`

### SPEC-020-06-SC03 — confirmation par WhatsApp

Critères : FEAT-020-AC12

- **Étant donné** ce compte _(v3, 2026-11-26, FEAT-023 : plus de code reçu en réponse à « Code DJAFAT »)_
- **Quand** `POST /me/phone/verify` reçoit `channel: 'whatsapp'`
- **Alors** il est refusé (422) : par WhatsApp le client envoie un code depuis son numéro, et c'est ce
  message qui confirme le numéro (SPEC-023-02-SC07, SPEC-023-03-SC05)

### SPEC-020-06-SC04 — un code lié à un autre compte ne vaut pas

Critères : FEAT-020-AC12

- **Étant donné** deux comptes A et B, et un code `verify_phone` demandé par A
- **Quand** B le vérifie
- **Alors** la réponse est 401 `OTP_INVALID` et le numéro de B reste non confirmé

### SPEC-020-06-SC05 — connexion par code sur un numéro non confirmé d'un compte e-mail

Critères : FEAT-020-AC13

- **Étant donné** le compte de SC01, numéro non confirmé
- **Quand** quelqu'un se connecte par un bon code SMS sur `+23566123456`
- **Alors** il répond 409 `PHONE_NOT_CONFIRMED`, aucune session n'est créée et le numéro reste non
  confirmé _(v3, 2026-11-26 : par WhatsApp, le message de ce numéro répond « numéro confirmé sur aucun
  compte » sans rien ouvrir — SPEC-023-02-SC03)_

### SPEC-020-06-SC06 — après confirmation, le code SMS ouvre ce compte

Critères : FEAT-020-AC12, FEAT-020-AC13

- **Étant donné** le compte de SC02, numéro confirmé
- **Quand** il se connecte par un bon code SMS sur ce numéro
- **Alors** la session s'ouvre sur ce compte

### SPEC-020-06-SC07 — comptes créés par téléphone : inchangés

Critères : FEAT-020-AC13

- **Étant donné** un compte sans e-mail ni mot de passe (créé par code, ou par une commande au téléphone)
- **Quand** il se connecte par un bon code SMS
- **Alors** la session s'ouvre comme aujourd'hui

### SPEC-020-06-SC08 — commande au téléphone sur un numéro non confirmé d'un compte e-mail

Critères : FEAT-020-AC13

- **Étant donné** un compte créé par e-mail, avec mot de passe, dont le numéro `+235 66 12 34 56` n'est pas confirmé
- **Quand** un opérateur prend une commande au téléphone pour ce numéro ; puis, le numéro confirmé, à nouveau
- **Alors** la première répond 409 `PHONE_NOT_CONFIRMED`, sans confirmer le numéro ni enregistrer d'adresse ou de commande ; la seconde est prise

## Erreurs et cas limites

- 401 `OTP_INVALID`, 409 `PHONE_NOT_CONFIRMED`, 429 `RATE_LIMITED`, 503 `SMS_UNAVAILABLE`.
- Le code de connexion consommé par un refus R4 ne revient pas : il faut en demander un autre.
- Changer de numéro reste hors périmètre : `request` et `verify` confirment le numéro du compte.

## Contrats API et données

- Routes _nouvelles_ ci-dessus ; schémas `dto/phone-link.schema.ts` (_nouveau_).
- Code d'erreur `PHONE_NOT_CONFIRMED` (partagé avec SPEC-020-04).
- Audit `AUTH_PHONE_VERIFIED` (_nouveau_). Le but de code `verify_phone` (_nouveau_) remplace
  l'usage prévu de `change_phone`, qui reste déclaré.

## Autorisations

Routes `/me/phone/*` : connecté, sur son propre compte. Connexions par code : publiques, inchangées
sauf R4.

## Hypothèses et questions ouvertes

- Technique : R4 révèle au détenteur du numéro qu'un compte e-mail utilise ce numéro ; il a prouvé
  qu'il détient le numéro, ce qui est acceptable. La correction d'un numéro mal saisi passe par le
  support tant que le changement de numéro n'existe pas.
