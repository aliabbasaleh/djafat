# SPEC-020-05 — Mot de passe oublié, définir ou changer son mot de passe

## Comportement observable

Aujourd'hui rien de tout cela n'existe. `SessionService.revokeAllForUser`
(`session.service.ts:208-214`) sait déjà révoquer toutes les sessions d'un compte.

Après la spec :

- `POST /v1/auth/password/forgot { email }` → toujours 202 (_nouveau_, public) ;
- `POST /v1/auth/password/reset { email, code, password }` → 200, la réponse de connexion
  habituelle avec `deviceToken` (_nouveau_, public) ;
- `PUT /v1/me/password { currentPassword?, newPassword }` → 204 (_nouveau_, connecté).

## Règles métier

- R1 — `forgot` : un code `reset_password` part seulement si l'adresse est vérifiée sur un compte non supprimé ; sinon rien n'est envoyé, même réponse. _(v2, revue n° 4)_ Toute adresse dépense le même budget par adresse et rencontre le même verrou (429 et 423 identiques) ; le code part en arrière-plan, et un échec d'envoi est journalisé sans changer la réponse ni son délai.
- R2 — `reset` : le nouveau mot de passe passe la règle de SPEC-020-02 (contexte : l'adresse donnée) **avant** la vérification du code, pour qu'un mot de passe refusé ne fasse pas perdre le code. Un mauvais code, ou une adresse sans compte : 401 `OTP_INVALID`.
- R3 — `reset` réussi : le hachage est remplacé, toutes les sessions du compte sont révoquées (`password_reset`), tous ses appareils mémorisés aussi, puis une session s'ouvre sur cet appareil, qui est mémorisé. L'avis « mot de passe modifié » part à l'adresse ; audit `AUTH_PASSWORD_RESET` (_nouveau_).
- R4 — `PUT /me/password` pour un compte qui a un mot de passe : `currentPassword` est exigé et doit vérifier, sinon 403 `CURRENT_PASSWORD_INCORRECT` (_nouveau_ ; 403 et non 401, pour que le SDK n'y voie pas une session expirée). Chaque échec compte sur le verrou de l'adresse du compte (423 `OTP_LOCKED` une fois verrouillé).
- R5 — Pour un compte sans mot de passe (créé par WhatsApp ou SMS) : `currentPassword` n'est pas demandé, mais une adresse vérifiée est exigée, puisque la connexion par mot de passe passe par l'e-mail ; sinon 409 `EMAIL_REQUIRED` (_nouveau_), « Ajoutez d'abord votre adresse e-mail. »
- R6 — Le nouveau mot de passe passe la règle de SPEC-020-02 avec le contexte du compte (e-mail, téléphone, nom) ; refus : 422 sur `newPassword`.
- R7 — Changement réussi : hachage remplacé, toutes les autres sessions révoquées (la session courante reste), appareils mémorisés révoqués, avis « mot de passe modifié » envoyé, audit `AUTH_PASSWORD_CHANGED` (_nouveau_, avec `first: true` pour un premier mot de passe).

## Scénarios

### SPEC-020-05-SC01 — demande de réinitialisation

Critères : FEAT-020-AC10

- **Étant donné** un compte à l'adresse vérifiée `awa@example.td`, et une adresse inconnue
- **Quand** une réinitialisation est demandée pour chacune
- **Alors** les deux répondent 202 ; seule `awa@example.td` reçoit un code `reset_password`

### SPEC-020-05-SC02 — réinitialisation réussie

Critères : FEAT-020-AC10, FEAT-020-AC15

- **Étant donné** ce compte avec deux sessions ouvertes et un appareil mémorisé, et son code de réinitialisation
- **Quand** la réinitialisation est faite avec un nouveau mot de passe valable
- **Alors** l'ancien mot de passe est refusé et le nouveau accepté ; les deux sessions et l'appareil sont révoqués ; une nouvelle session et un `deviceToken` sont rendus ; l'avis part ; `AUTH_PASSWORD_RESET` est écrit

### SPEC-020-05-SC03 — mauvais code

Critères : FEAT-020-AC10

- **Étant donné** ce compte
- **Quand** la réinitialisation est faite avec un mauvais code
- **Alors** la réponse est 401 `OTP_INVALID` et le mot de passe ne change pas

### SPEC-020-05-SC04 — mot de passe refusé avant le code

Critères : FEAT-020-AC10

- **Étant donné** un code de réinitialisation valable
- **Quand** la réinitialisation est faite avec « motdepasse »
- **Alors** la réponse est 422 sur `password`, et le même code reste utilisable ensuite

### SPEC-020-05-SC05 — changer son mot de passe

Critères : FEAT-020-AC11, FEAT-020-AC15

- **Étant donné** un compte connecté sur deux appareils (sessions S1 et S2), avec mot de passe
- **Quand** S1 change le mot de passe en donnant le bon mot de passe actuel
- **Alors** la réponse est 204 ; S2 est révoquée, S1 reste valable ; l'avis part ; `AUTH_PASSWORD_CHANGED` est écrit

### SPEC-020-05-SC06 — mauvais mot de passe actuel

Critères : FEAT-020-AC11

- **Étant donné** le compte de SC05
- **Quand** S1 change le mot de passe avec un mauvais mot de passe actuel
- **Alors** la réponse est 403 `CURRENT_PASSWORD_INCORRECT`, le mot de passe ne change pas, un échec compte sur le verrou

### SPEC-020-05-SC07 — premier mot de passe d'un compte WhatsApp

Critères : FEAT-020-AC11

- **Étant donné** un compte créé par WhatsApp, sans mot de passe, avec puis sans adresse vérifiée
- **Quand** il définit un mot de passe sans `currentPassword`
- **Alors** avec l'adresse : 204 et `hasPassword: true` ; sans l'adresse : 409 `EMAIL_REQUIRED`

### SPEC-020-05-SC08 — de bout en bout sur PostgreSQL

Critères : FEAT-020-AC10

- **Étant donné** l'API réelle et le compte de SPEC-020-03-SC10
- **Quand** il demande une réinitialisation, la fait avec le code lu dans Redis, puis se connecte par mot de passe
- **Alors** l'ancien refresh répond 401, et la connexion avec le nouveau mot de passe réussit

### SPEC-020-05-SC09 — adresse connue ou inconnue : mêmes limites

Critères : FEAT-020-AC10

- **Étant donné** une adresse vérifiée et une adresse inconnue
- **Quand** « Mot de passe oublié ? » est demandé quatre fois pour chacune ; puis les deux sont verrouillées
- **Alors** les trois premières demandes répondent 202 et la quatrième 429, pour les deux ; verrouillées, les deux répondent 423 ; seule l'adresse vérifiée reçoit des codes

## Erreurs et cas limites

- 202 / 401 `OTP_INVALID` / 403 `CURRENT_PASSWORD_INCORRECT` / 409 `EMAIL_REQUIRED` / 422 /
  423 `OTP_LOCKED` / 429 `RATE_LIMITED` / 503 `OTP_DELIVERY_FAILED`.
- Si l'avis ne part pas (SMTP en panne), le changement est quand même fait (SPEC-020-01 R6).

## Contrats API et données

- Routes _nouvelles_ ci-dessus ; schémas dans `dto/password.schema.ts`.
- Codes d'erreur `CURRENT_PASSWORD_INCORRECT`, `EMAIL_REQUIRED` (_nouveaux_).
- Audits `AUTH_PASSWORD_RESET`, `AUTH_PASSWORD_CHANGED` (_nouveaux_).
- `SessionService` gagne la révocation de toutes les sessions sauf une (_nouveau_).

## Autorisations

`forgot` et `reset` : publics, limités en débit. `PUT /me/password` : connecté, sur son propre
compte seulement (l'identité vient du jeton, jamais du corps).

## Hypothèses et questions ouvertes

- Technique : après une réinitialisation, la session s'ouvre directement (le code prouve l'accès à
  la boîte, comme une connexion par code) au lieu de renvoyer le client vers la connexion.
- Technique : un changement de mot de passe révoque aussi les appareils mémorisés ; le prochain
  mot de passe sur cet appareil redemandera un code.
