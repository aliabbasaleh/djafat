# SPEC-020-12 — Changer son e-mail sans laisser prendre son compte

## Comportement observable

Ajouter ou changer son e-mail se fait dans « Mon profil » (FEAT-007 : `POST /me/email`, puis
`POST /me/email/verify` avec le code reçu à la nouvelle adresse). Depuis FEAT-020, l'e-mail est à
la fois l'identifiant de connexion et l'adresse de secours : avec une session volée, le changer
puis faire « Mot de passe oublié ? » donnait le compte. Après (décision FEAT-020-Q28, revue n° 6) :

## Règles métier

- R1 — Un compte qui a un mot de passe le donne pour changer d'e-mail (`currentPassword`) :
  absent ou faux, 403 `CURRENT_PASSWORD_INCORRECT` et aucun code ; mêmes verrou et seuil que pour
  changer de mot de passe (10 échecs, 15 min, puis 423). Un compte sans mot de passe ajoute son
  e-mail comme avant.
- R2 — Quand le bon code remplace une adresse vérifiée par une autre, l'ancienne adresse reçoit
  l'alerte « L'adresse e-mail de votre compte DJAFAT a été changée », avec la nouvelle adresse
  masquée, la date et l'heure de N'Djamena, et quoi faire si ce n'est pas vous.
- R3 — Dans ce cas, les appareils mémorisés du compte sont oubliés : la prochaine connexion par mot
  de passe redemande un code. Audit `AUTH_EMAIL_CHANGED` (_nouveau_). Une première adresse
  (aucune vérifiée avant) : ni alerte, ni appareils oubliés.
- R4 — Le code `verify_email` est lié au compte qui l'a demandé : un code demandé par un autre
  compte ne confirme jamais l'adresse ici (401 `OTP_INVALID`). Sans cela, un pirate demanderait le
  code depuis son propre compte et le confirmerait avec une session volée. _(v2, revue 2 n° 3)_

## Scénarios

### SPEC-020-12-SC01 — sans le bon mot de passe : refus

Critères : FEAT-020-AC17

- **Étant donné** un compte avec mot de passe
- **Quand** il demande à changer d'e-mail sans mot de passe, puis avec un faux
- **Alors** 403 `CURRENT_PASSWORD_INCORRECT` les deux fois, et aucun code n'est envoyé

### SPEC-020-12-SC02 — avec le bon mot de passe : code à la nouvelle adresse

Critères : FEAT-020-AC17

- **Étant donné** le même compte
- **Quand** il demande à changer d'e-mail avec son mot de passe
- **Alors** un code `verify_email` part à la nouvelle adresse

### SPEC-020-12-SC03 — compte sans mot de passe : comme avant

Critères : FEAT-020-AC17

- **Étant donné** un compte sans mot de passe ni e-mail
- **Quand** il ajoute un e-mail
- **Alors** le code part sans qu'aucun mot de passe soit demandé

### SPEC-020-12-SC04 — adresse remplacée : alerte et appareils oubliés

Critères : FEAT-020-AC17

- **Étant donné** un compte à l'adresse vérifiée `awa@example.td`, avec mot de passe
- **Quand** il confirme une nouvelle adresse avec le bon code ; puis un compte sans adresse confirme
  sa première
- **Alors** `awa@example.td` reçoit l'alerte avec la nouvelle adresse masquée, les appareils
  mémorisés sont oubliés et l'audit `AUTH_EMAIL_CHANGED` est écrit ; pour la première adresse, ni
  alerte ni appareils oubliés

### SPEC-020-12-SC05 — verrou après dix faux mots de passe

Critères : FEAT-020-AC17

- **Étant donné** un compte avec mot de passe
- **Quand** dix demandes ont un faux mot de passe, puis une a le bon
- **Alors** la onzième répond 423 `OTP_LOCKED`

### SPEC-020-12-SC06 — « Mon profil » demande le mot de passe actuel [evidence: manual]

Critères : FEAT-020-AC17

- **Étant donné** un client connecté qui a un mot de passe, sur « Mon profil »
- **Quand** il veut changer d'e-mail
- **Alors** le champ « Mot de passe actuel » apparaît sous la nouvelle adresse ; un faux mot de
  passe affiche « Mot de passe actuel incorrect. »

### SPEC-020-12-SC07 — un code demandé par un autre compte ne vaut pas

Critères : FEAT-020-AC17

- **Étant donné** un pirate qui a demandé, depuis son propre compte, un code pour son adresse
- **Quand** il essaie ce code avec la session volée d'un autre compte
- **Alors** 401 `OTP_INVALID` ; l'e-mail de ce compte ne change pas et aucune alerte ne part

## Erreurs et cas limites

403 `CURRENT_PASSWORD_INCORRECT`, 423 `OTP_LOCKED`, 409 `EMAIL_ALREADY_USED` (inchangé), 401
`OTP_INVALID` pour un mauvais code. Une alerte qui ne peut pas partir est journalisée et ne fait
pas échouer le changement (avis « au mieux », SPEC-020-01).

## Contrats API et données

`POST /me/email` accepte `currentPassword` (facultatif, 1024 caractères au plus), `.strict()` ;
réponse inchangée. Nouvel avis `email_changed` (`account-notice.port.ts`). SDK :
`requestEmailVerification(email, currentPassword?)`.

## Autorisations

`@RequireAuth()` comme avant ; l'identité vient du jeton.

## UI et accessibilité

Le champ « Mot de passe actuel » (`autocomplete="current-password"`) n'apparaît que pour un compte
qui a un mot de passe ; les erreurs passent par `accountErrorMessage`. Après un remplacement, le
message dit que l'ancienne adresse a reçu une alerte et que les appareils redemanderont un code.
