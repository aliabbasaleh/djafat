# SPEC-020-04 — Se connecter avec e-mail et mot de passe, code sur un nouvel appareil

## Comportement observable

Aujourd'hui aucune connexion par mot de passe n'existe ; seules les connexions par code (SMS,
WhatsApp, e-mail) ouvrent une session (`auth.controller.ts:56-114`). Rien ne mémorise un appareil.

Après la spec, trois routes publiques (_nouvelles_) :

- `POST /v1/auth/password/login { email, password, deviceToken? }` → 200, soit
  `{ status: 'signed_in', access, refresh, user, … }`, soit
  `{ status: 'code_required', challengeId, expiresAt, sentTo, channels }` ;
- `POST /v1/auth/password/challenge/send { challengeId, channel }` → 202 ;
- `POST /v1/auth/password/challenge/verify { challengeId, channel, code, rememberDevice }` → 200,
  la réponse de connexion habituelle, plus `deviceToken` et `deviceTokenExpiresAt` si l'appareil
  est mémorisé.

## Règles métier

- R1 — Identifiants valables : un compte non supprimé dont l'adresse **vérifiée** est `email`, qui a un mot de passe, et dont le mot de passe vérifie. Tout autre cas — adresse inconnue, compte sans mot de passe, mauvais mot de passe — répond 401 `INVALID_CREDENTIALS` (_nouveau_), « E-mail ou mot de passe incorrect. ». Quand aucun hachage n'existe, un calcul factice garde le même temps de réponse.
- R2 — Chaque échec compte sur le verrou de l'adresse (`auth_target_locks`, mêmes seuils que les codes : `phone_lock_threshold`, `phone_lock_duration_seconds`), pour une adresse connue comme inconnue. Adresse verrouillée : 423 `OTP_LOCKED`, même avec le bon mot de passe, jusqu'à la fin du verrou. Un bon mot de passe remet le compteur à zéro. Les tentatives sont aussi limitées par réseau (`password_login_rate_limit_per_ip`, _nouveau_ réglage, 50 par 15 min par défaut) : 429 `RATE_LIMITED`.
- R3 — Bon mot de passe sur un compte non actif : 403 `ACCOUNT_INACTIVE`, aucun code envoyé.
- R4 — Bon mot de passe et `deviceToken` valable pour **ce** compte (non expiré, non révoqué) : la session s'ouvre (`status: 'signed_in'`) par le chemin commun ; l'appareil note sa dernière utilisation.
- R5 — Sinon : une connexion en attente (`auth_challenges`, genre `password_login`, valable 10 minutes) est créée, et un code `login_device` **lié** à elle part à l'adresse vérifiée du compte. La réponse dit où il est parti (`sentTo: { channel: 'email', destination: 'a***@gmail.com' }`) et liste les canaux.
- R6 — Canaux d'une connexion en attente : `email` toujours utilisable ; `sms` utilisable si le numéro du compte est confirmé et le SMS actif ; `whatsapp` utilisable si le numéro est confirmé et WhatsApp actif (avec le lien `wa.me` de FEAT-008). Un canal inutilisable est listé avec `available: false` (l'écran affiche « Bientôt disponible », FEAT-020-Q05).
- R7 — `challenge/send` : un nouveau code lié, sur `email` ou `sms`, vers la destination vérifiée du compte. WhatsApp n'est pas envoyé par DJAFAT : le client écrit « Code DJAFAT » (FEAT-008). Connexion en attente inconnue, expirée ou consommée : 401 `OTP_INVALID`. `sms` sans numéro confirmé : 409 `PHONE_NOT_CONFIRMED` (_nouveau_) ; SMS éteint : 503 `SMS_UNAVAILABLE`. _(v2, 2026-11-26, FEAT-023 : par WhatsApp, l'écran demande un code à **envoyer** pour cette connexion — `POST /auth/whatsapp/start` avec `challengeId`, SPEC-023-01 R7 ; plus de « Code DJAFAT ».)_
- R8 — `challenge/verify` : `email` et `sms` vérifient le code `login_device` lié à cette connexion ; `whatsapp` vérifie le code de connexion WhatsApp du numéro confirmé du compte. Le bon code consomme la connexion en attente (usage unique) et ouvre la session. _(v2, 2026-11-26, FEAT-023 : `whatsapp` n'est plus un code tapé — `challenge/verify` le refuse (422) ; le message du client termine la connexion, SPEC-023-03 R5.)_
- R9 — Mémoriser l'appareil : un jeton aléatoire de 32 octets, rendu une seule fois, dont seul un HMAC est stocké (`trusted_devices`, _nouvelle_ table), valable `trusted_device_ttl_seconds` (_nouveau_ réglage, 30 jours). `rememberDevice: false` n'en crée pas. Audit `AUTH_DEVICE_TRUSTED` (_nouveau_).
- R10 — Comme pour l'inscription, chaque nouvelle connexion en attente supprime d'abord les lignes expirées de `auth_challenges` (FEAT-020-Q15).
- R11 — Audit : `AUTH_LOGIN_FAILURE` (raison `bad_credentials`, sans adresse en clair) à chaque échec ; `AUTH_LOGIN_SUCCESS` par le chemin commun.

## Scénarios

### SPEC-020-04-SC01 — appareil mémorisé : connexion directe

Critères : FEAT-020-AC06

- **Étant donné** un compte avec mot de passe et un `deviceToken` mémorisé pour lui il y a 3 jours
- **Quand** il se connecte avec son e-mail, son mot de passe et ce jeton
- **Alors** la réponse est `signed_in` avec des jetons de session, et aucun code n'est envoyé

### SPEC-020-04-SC02 — nouvel appareil : code demandé par e-mail

Critères : FEAT-020-AC06, FEAT-020-AC09

- **Étant donné** ce compte, au numéro non confirmé, sans `deviceToken`
- **Quand** il se connecte avec le bon mot de passe
- **Alors** la réponse est `code_required` avec `sentTo.destination` masquée ; un code `login_device` lié à la connexion en attente part à l'adresse ; `channels` vaut `email` utilisable, `sms` et `whatsapp` non utilisables

### SPEC-020-04-SC03 — bon code : session et appareil mémorisé

Critères : FEAT-020-AC06, FEAT-020-AC15

- **Étant donné** la connexion en attente de SC02 et son code
- **Quand** il est vérifié avec `rememberDevice: true`
- **Alors** la session s'ouvre, un `deviceToken` valable 30 jours est rendu, l'audit `AUTH_DEVICE_TRUSTED` est écrit ; une connexion suivante avec ce jeton suit SC01

### SPEC-020-04-SC04 — sans « Se souvenir de cet appareil »

Critères : FEAT-020-AC06

- **Étant donné** la connexion en attente de SC02
- **Quand** le code est vérifié avec `rememberDevice: false`
- **Alors** la session s'ouvre et aucun `deviceToken` n'est rendu

### SPEC-020-04-SC05 — trois échecs, une seule réponse

Critères : FEAT-020-AC07, FEAT-020-AC15

- **Étant donné** une adresse inconnue, un compte sans mot de passe, et un mauvais mot de passe sur un compte qui en a un
- **Quand** chacun tente de se connecter
- **Alors** les trois répondent 401 `INVALID_CREDENTIALS` avec le même message, comptent un échec sur le verrou de l'adresse et écrivent `AUTH_LOGIN_FAILURE`

### SPEC-020-04-SC06 — verrou après trop d'échecs

Critères : FEAT-020-AC07

- **Étant donné** 10 échecs sur une adresse (seuil par défaut)
- **Quand** le bon mot de passe est ensuite donné
- **Alors** la réponse est 423 `OTP_LOCKED` jusqu'à la fin du verrou, puis la connexion redevient possible

### SPEC-020-04-SC07 — jeton d'appareil refusé

Critères : FEAT-020-AC06

- **Étant donné** un jeton expiré (plus de 30 jours), un jeton révoqué, et le jeton valable d'un autre compte
- **Quand** chacun accompagne le bon mot de passe
- **Alors** les trois répondent `code_required`

### SPEC-020-04-SC08 — compte suspendu

Critères : FEAT-020-AC07

- **Étant donné** un compte suspendu avec mot de passe
- **Quand** il se connecte avec le bon mot de passe
- **Alors** la réponse est 403 `ACCOUNT_INACTIVE` et aucun code n'est envoyé

### SPEC-020-04-SC09 — usage unique et liaison

Critères : FEAT-020-AC06

- **Étant donné** deux connexions en attente C1 et C2 du même compte
- **Quand** le code de C1 est vérifié pour C2, puis pour C1 deux fois
- **Alors** le premier essai est refusé (`OTP_INVALID`), le deuxième ouvre la session, le troisième est refusé (`OTP_INVALID`)

### SPEC-020-04-SC10 — canaux par téléphone quand le numéro est confirmé

Critères : FEAT-020-AC09

- **Étant donné** un compte au numéro confirmé, SMS actif, et une connexion en attente
- **Quand** le code est demandé par `sms`, puis vérifié par `sms`
- **Alors** un code lié part au numéro et la session s'ouvre ; sur un compte au numéro non confirmé, la demande par `sms` répond 409 `PHONE_NOT_CONFIRMED`

### SPEC-020-04-SC11 — de bout en bout sur PostgreSQL

Critères : FEAT-020-AC06, FEAT-020-AC07

- **Étant donné** l'API réelle et un compte créé par SPEC-020-03-SC10, avec son `deviceToken`
- **Quand** il se connecte par mot de passe avec puis sans ce jeton, puis vérifie le code du second essai
- **Alors** le premier essai est `signed_in`, le second `code_required`, puis `signed_in` après le code

## Erreurs et cas limites

- 401 `INVALID_CREDENTIALS`, 401 `OTP_INVALID`, 403 `ACCOUNT_INACTIVE`, 409 `PHONE_NOT_CONFIRMED`,
  423 `OTP_LOCKED`, 429 `RATE_LIMITED`, 503 `OTP_DELIVERY_FAILED` / `SMS_UNAVAILABLE`, 422.
- Le verrou de l'adresse est partagé avec ses codes e-mail : trop d'échecs bloquent aussi la
  connexion par code pendant 15 minutes, ce qui est voulu (un seul compteur par cible).
- Un `deviceToken` mal formé est traité comme absent.

## Contrats API et données

- Routes _nouvelles_ ci-dessus ; schémas `dto/password.schema.ts` (_nouveau_).
- Codes d'erreur `INVALID_CREDENTIALS`, `PHONE_NOT_CONFIRMED` (_nouveaux_).
- Réglages `password_login_rate_limit_per_ip` et `trusted_device_ttl_seconds` (_nouveaux_) dans
  `PLATFORM_SETTINGS_DEFAULTS` (`packages/config/src/constants.ts:21-60`), lus par `PlatformService`.
- Table `trusted_devices` (_nouvelle_) : `id`, `user_id`, `token_hash` unique, `label`,
  `created_at`, `last_used_at`, `expires_at`, `revoked_at`, `revoked_reason`.
- Table `auth_challenges` (genre `password_login`) : voir SPEC-020-03.

## Hypothèses et questions ouvertes

- Technique : le code de nouvel appareil part tout de suite à l'e-mail (pas de clic de plus) ;
  le client peut le redemander, ou choisir un autre canal utilisable.
- Technique : un appareil est mémorisé pour un compte ; un navigateur garde un seul jeton (le
  dernier compte). Deux comptes sur un même appareil redemanderont parfois un code.
- Technique : « Se déconnecter partout » ne révoque pas les appareils mémorisés (inchangé) ; le
  mot de passe reste exigé sur eux.
