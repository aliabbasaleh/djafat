# SPEC-005-02 — Les endpoints OTP acceptent un numéro écrit à la tchadienne

## Comportement observable

Aujourd'hui, `OtpRequestSchema` et `OtpVerifySchema`
(`apps/api/src/modules/auth/dto/otp-request.schema.ts`) valident `phone` avec
`PhoneSchema` (E.164 strict) : `66 12 34 56` produit une erreur 422
`VALIDATION_ERROR`.

Après : le champ `phone` est validé par un schéma qui normalise selon
`LAUNCH_MARKET` (SPEC-005-01). Le service reçoit toujours un E.164. Une saisie
non normalisable reste refusée en 422 `VALIDATION_ERROR`, avec un message qui
explique le format attendu.

## Règles métier

- R1 — La demande et la vérification utilisent la même normalisation.
- R2 — Le service OTP ne reçoit jamais autre chose qu'un E.164.
- R3 — Le message d'erreur cite le format attendu (8 chiffres, ou `+` suivi de l'indicatif).

## Scénarios

### SPEC-005-02-SC01 — demande de code avec un numéro national

Critères : FEAT-005-AC01

- **Étant donné** le corps `{ phone: "66 12 34 56", purpose: "login" }`
- **Quand** il est validé par le schéma de demande de code
- **Alors** il est accepté et `phone` vaut `+23566123456`

### SPEC-005-02-SC02 — demande et vérification avec deux écritures différentes

Critères : FEAT-005-AC05

- **Étant donné** une demande avec `00235 66 12 34 56` et une vérification avec `٦٦١٢٣٤٥٦` et le code `123456`
- **Quand** les deux corps sont validés
- **Alors** les deux `phone` valent `+23566123456`

### SPEC-005-02-SC03 — saisie invalide refusée avec un message explicite

Critères : FEAT-005-AC04

- **Étant donné** le corps `{ phone: "6612345", purpose: "login" }`
- **Quand** il est validé
- **Alors** il est refusé, avec un message qui mentionne les 8 chiffres attendus

### SPEC-005-02-SC04 — le schéma reste strict sur les autres champs

Critères : FEAT-005-AC04

- **Étant donné** un corps valide avec un champ inconnu en plus
- **Quand** il est validé
- **Alors** il est refusé (`.strict()` conservé)

## Erreurs et cas limites

`phone` absent ou non textuel : refusé comme avant.

## Contrats API et données

`POST /v1/auth/otp/request` et `POST /v1/auth/otp/verify` acceptent désormais
plus de formats en entrée. La réponse (`user.phone`) reste en E.164. Pas de
changement de schéma de base.
