# SPEC-004-02 — Chaque application branche ses déconnexions sur le SDK

## Comportement observable

Aujourd'hui, chaque déconnexion se contente d'effacer la session locale, sans
appeler le serveur :

- `apps/web/src/components/CartIndicator.tsx:61` : `clearSession()` ;
- `apps/admin/src/app/admin/layout.tsx:41` : `clearSession()` ;
- `apps/restaurant/src/app/restaurant/layout.tsx:42` : `clearSession()` ;
- `apps/courier/lib/auth-context.tsx` : `signOut()`, qui efface `SecureStore` ;
- `apps/mobile/lib/auth-context.tsx` : `signOut()`, qui efface `SecureStore`.

Après : chacun passe par `api.auth.signOut({ refresh, clearLocal })` (SPEC-004-01),
avec le jeton de rafraîchissement stocké par l'app et sa propre fonction d'effacement.

Les `clearSession()` déclenchés **sur une réponse 401** (session déjà morte côté
serveur) restent inchangés : il n'y a rien à révoquer.

## Règles métier

- R1 — Seules les déconnexions voulues par l'utilisateur, plus le `signOut` des contextes mobiles, passent par le SDK.
- R2 — Chaque application garde son propre stockage (espaces de noms distincts) ; le SDK ne connaît pas le stockage.
- R3 — L'écran de connexion n'est affiché qu'après la fin de `signOut`.

## Scénarios

### SPEC-004-02-SC01 — web, admin, restaurant : le bouton passe par le SDK [evidence: review]

Critères : FEAT-004-AC04

- **Étant donné** les boutons « Déconnexion » de web, admin et restaurant
- **Quand** on suit leur gestionnaire
- **Alors** ils appellent `signOut()` de `lib/session.ts`, qui appelle `api.auth.signOut` avec `getRefreshToken()` et `clearSession`. Vérifié en revue : ces apps n'ont pas de tests de composants, et la logique elle-même est testée dans SPEC-004-01

### SPEC-004-02-SC02 — livreur et mobile : le contexte passe par le SDK [evidence: review]

Critères : FEAT-004-AC04

- **Étant donné** `signOut` dans `lib/auth-context.tsx` des apps courier et mobile
- **Quand** on le suit
- **Alors** il lit la session stockée, appelle `api.auth.signOut({ refresh, clearLocal: clearSession })`, puis remet l'état à « signed-out ». Vérifié en revue : un contexte React Native n'est pas testable sans environnement Expo, et `expo export` est en échec préexistant

### SPEC-004-02-SC03 — chaque app sait relire son jeton de rafraîchissement

Critères : FEAT-004-AC04

- **Étant donné** une session stockée dans le `localStorage` de web, admin ou restaurant
- **Quand** `getRefreshToken()` est appelé
- **Alors** il renvoie le jeton de rafraîchissement stocké, ou `null` hors navigateur ou si le stockage est bloqué

## Erreurs et cas limites

Stockage bloqué (navigation privée) : `getRefreshToken()` renvoie `null`. La
révocation est quand même tentée avec le jeton d'accès, et l'effacement local a
lieu de toute façon.

## Contrats API et données

Aucun nouveau contrat serveur. Dans chaque app web, une nouvelle fonction
`getRefreshToken()` et un nouveau `lib/session.ts`.
