# SPEC-004-01 — Fin de session dans le SDK : révoquer puis toujours effacer

## Comportement observable

Aujourd'hui, aucun client n'appelle `/auth/logout`. Le SDK (`packages/sdk/src/index.ts:44`)
n'expose aucune méthode d'authentification ; les apps appellent `/auth/otp/*`
directement via `api.http`.

Après : `api.auth.signOut({ refresh, clearLocal })` fait les opérations suivantes :

1. Il appelle `POST /auth/logout` avec le jeton d'accès courant (fourni par `getAccessToken`).
2. Si cet appel répond 401 et qu'un jeton de rafraîchissement est fourni, il appelle
   `POST /auth/refresh`, puis `POST /auth/logout` avec le **nouveau** jeton d'accès.
3. Il appelle toujours `clearLocal()`, quel que soit le résultat.
4. Il retourne un résultat, sans jamais lever d'erreur :
   - `{ revoked: true }` ;
   - ou `{ revoked: false, reason }`, avec `reason` parmi `already-invalid`, `network`, `server`.

## Règles métier

- R1 — La révocation serveur est tentée avant l'effacement local, car `/auth/logout` a besoin du jeton.
- R2 — L'effacement local a toujours lieu, même si l'appel lève une erreur ou que `clearLocal` est appelé après un échec réseau.
- R3 — Au plus un rafraîchissement, et uniquement après un 401 sur la révocation.
- R4 — Si l'accès et le rafraîchissement sont tous deux refusés (401), aucune session utilisable ne subsiste côté serveur : résultat `already-invalid`.
- R5 — `signOut` ne lève jamais d'erreur.

## Scénarios

### SPEC-004-01-SC01 — déconnexion nominale

Critères : FEAT-004-AC01, FEAT-004-AC03

- **Étant donné** une session avec un jeton d'accès valide `acc-1`
- **Quand** `signOut` est appelé
- **Alors** `POST /auth/logout` est envoyé avec `Authorization: Bearer acc-1`, **avant** `clearLocal`, puis `clearLocal` est appelé une fois et le résultat est `{ revoked: true }`

### SPEC-004-01-SC02 — jeton d'accès expiré : rafraîchir une fois, puis révoquer

Critères : FEAT-004-AC02

- **Étant donné** un jeton d'accès expiré (logout → 401) et un jeton de rafraîchissement valide
- **Quand** `signOut` est appelé
- **Alors** `POST /auth/refresh` est envoyé avec `{ refresh }`, puis `POST /auth/logout` avec le nouveau jeton d'accès renvoyé, le résultat est `{ revoked: true }` et `clearLocal` est appelé

### SPEC-004-01-SC03 — serveur injoignable : la session locale est quand même effacée

Critères : FEAT-004-AC03

- **Étant donné** une panne réseau
- **Quand** `signOut` est appelé
- **Alors** aucune erreur n'est levée, `clearLocal` est appelé et le résultat est `{ revoked: false, reason: 'network' }`

### SPEC-004-01-SC04 — accès et rafraîchissement tous deux refusés

Critères : FEAT-004-AC02, FEAT-004-AC03

- **Étant donné** logout → 401 et refresh → 401
- **Quand** `signOut` est appelé
- **Alors** un seul rafraîchissement est tenté, `clearLocal` est appelé et le résultat est `{ revoked: false, reason: 'already-invalid' }`

### SPEC-004-01-SC05 — erreur serveur : effacement local et résultat honnête

Critères : FEAT-004-AC03

- **Étant donné** logout → 500
- **Quand** `signOut` est appelé
- **Alors** aucun rafraîchissement n'est tenté, `clearLocal` est appelé et le résultat est `{ revoked: false, reason: 'server' }`

### SPEC-004-01-SC06 — pas de jeton de rafraîchissement : pas de tentative

Critères : FEAT-004-AC02

- **Étant donné** logout → 401 et aucun jeton de rafraîchissement
- **Quand** `signOut` est appelé
- **Alors** `/auth/refresh` n'est pas appelé, `clearLocal` est appelé et le résultat est `{ revoked: false, reason: 'already-invalid' }`

## Erreurs et cas limites

- `clearLocal` asynchrone (SecureStore) : il est attendu avant de retourner.
- `clearLocal` qui lève : l'erreur est propagée. C'est la seule possible, et elle
  est locale, sans lien avec le réseau.

## Contrats API et données

- Endpoints existants : `POST /v1/auth/logout` (204, bearer requis) et `POST /v1/auth/refresh` (`{ refresh }` → `{ access, accessExpiresAt, refresh, refreshExpiresAt }`).
- **Nouveau** dans le SDK : `RequestOptions.accessToken?: string`, qui remplace pour une requête le jeton de `getAccessToken`.
- **Nouveau** dans le SDK : `createAuthClient(http).signOut(...)`, exposé en `api.auth`.
