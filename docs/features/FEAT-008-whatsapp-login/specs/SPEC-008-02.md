# SPEC-008-02 — Recevoir les messages WhatsApp et répondre avec un code

## Comportement observable

- `GET /v1/auth/whatsapp/webhook?hub.mode=subscribe&hub.verify_token=…&hub.challenge=…` : renvoie `hub.challenge` en texte si le jeton est `WHATSAPP_VERIFY_TOKEN`, sinon 403.
- `POST /v1/auth/whatsapp/webhook` (appelé par Meta) : vérifie `X-Hub-Signature-256`, traite les messages, répond toujours 200 à une requête signée (sinon Meta relivre en boucle).

## Règles métier

- R1 — Signature : `sha256=` + HMAC-SHA256 du corps brut avec `WHATSAPP_APP_SECRET`, comparée en temps constant. Absente ou fausse → 401 et rien n'est traité. Sans secret configuré → 503 `WHATSAPP_UNAVAILABLE`.
- R2 — Seuls les messages texte dont le texte contient « code » (casse et accents ignorés) déclenchent un code. Les autres sont ignorés (Q02).
- R3 — L'expéditeur (`from`, chiffres sans `+`) doit être un numéro valide selon la même règle que la saisie (FEAT-005 : format tchadien ou international E.164) ; sinon ignoré (Q03).
- R4 — Ignorés : un message adressé à un autre `phone_number_id` que `WHATSAPP_PHONE_NUMBER_ID`, et un message de plus de 10 minutes (Q07).
- R5 — Un identifiant de message déjà traité dans les 24 h est ignoré (Q06).
- R6 — Le code est demandé à `OtpService` (canal `whatsapp`, cible = numéro E.164, objet `login`) : hachage, expiration, verrou et limite par numéro (partagée avec le SMS) s'appliquent.
- R7 — Plafond global : au-delà de `WHATSAPP_MAX_CODES_PER_HOUR` codes WhatsApp dans l'heure, plus aucun code n'est envoyé (Q05).
- R8 — Un refus (limite, verrou, plafond, échec d'envoi) est journalisé sans numéro complet ni code ; la réponse à Meta reste 200.

## Scénarios

### SPEC-008-02-SC01 — signature valide, message « Code DJAFAT » : code demandé

Critères : FEAT-008-AC03, FEAT-008-AC04

- **Étant donné** un message texte « Code DJAFAT » de `23566123456`, récent, pour notre numéro, correctement signé
- **Quand** le webhook le reçoit
- **Alors** un code `login` est demandé pour la cible WhatsApp `+23566123456`

### SPEC-008-02-SC02 — signature absente ou fausse : refusé, rien n'est traité

Critères : FEAT-008-AC03

- **Étant donné** le même corps avec une signature fausse, puis sans signature
- **Quand** le webhook le reçoit
- **Alors** il est refusé en 401 et aucun code n'est demandé

### SPEC-008-02-SC03 — vérification d'abonnement

Critères : FEAT-008-AC03

- **Étant donné** le jeton de vérification configuré
- **Quand** Meta appelle la vérification avec le bon jeton, puis avec un mauvais
- **Alors** le défi est renvoyé tel quel, puis la demande est refusée en 403

### SPEC-008-02-SC04 — messages ignorés

Critères : FEAT-008-AC04, FEAT-008-AC07

- **Étant donné** un message « bonjour », un message d'un numéro invalide (tchadien trop court), un message vieux de 11 minutes, un message pour un autre numéro professionnel et un message d'image
- **Quand** le webhook les reçoit, signés
- **Alors** aucun code n'est demandé

### SPEC-008-02-SC05 — même message livré deux fois : un seul code

Critères : FEAT-008-AC07

- **Étant donné** un message déjà traité
- **Quand** Meta le relivre avec le même identifiant
- **Alors** un seul code a été demandé

### SPEC-008-02-SC06 — plafond horaire atteint, ou limite par numéro : rien n'est envoyé, Meta reçoit 200

Critères : FEAT-008-AC04

- **Étant donné** le plafond horaire épuisé, puis un `OtpService` qui refuse (limite par numéro)
- **Quand** un message valide arrive
- **Alors** aucun code n'est envoyé et le traitement se termine sans erreur

## Erreurs et cas limites

Plusieurs messages dans une même livraison sont traités un par un ; l'échec de l'un n'empêche pas les autres.

## Contrats API et données

Routes **nouvelles** : `GET` et `POST /v1/auth/whatsapp/webhook`. Canal **nouveau** `whatsapp` dans `otp_codes`. Code d'erreur **nouveau** : `WHATSAPP_UNAVAILABLE`.

## Autorisations

Publiques côté HTTP ; l'authenticité vient de la signature Meta (R1).
