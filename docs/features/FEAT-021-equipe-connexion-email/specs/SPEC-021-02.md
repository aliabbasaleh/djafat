# SPEC-021-02 — Règles communes : e-mail et mot de passe, rôle de l'application, codes par téléphone

## Comportement observable

La console admin, la console restaurant et l'application livreur se connectent toutes trois par
e-mail et mot de passe, avec les routes de FEAT-020 déjà en place, et proposent les codes par
téléphone seulement quand le serveur les déclare disponibles. Ce qui est commun aux trois est une
logique cliente partagée dans `@djafat/sdk` ; chaque application garde son écran (SPEC-021-03,
SPEC-021-04).

## Règles métier

- R1 — Connexion : e-mail et mot de passe → `POST /auth/password/login`, avec le jeton d'appareil
  mémorisé par **cette** application s'il existe.
- R2 — Réponse `code_required` : étape du code, avec l'adresse masquée, la case « Se souvenir de cet
  appareil (30 jours) » et « Renvoyer le code » après 60 s → `POST /auth/password/challenge/verify`.
- R3 — Session obtenue (directement, après le code, ou après une réinitialisation) : si le compte
  n'a pas le rôle de l'application (`hasAdminAccess`, `hasRestaurantAccess`, `hasCourierAccess`),
  rien n'est gardé, ni session ni appareil, et l'application affiche son message de refus actuel ;
  sinon la session est gardée comme aujourd'hui, et le jeton d'appareil sous une clé propre à
  l'application, conservée à la déconnexion.
- R4 — « Mot de passe oublié ? » : e-mail → `POST /auth/password/forgot` (même réponse que
  l'adresse existe ou non) → code et nouveau mot de passe (règles de FEAT-020 :
  `validateNewPassword`) → `POST /auth/password/reset`, qui connecte → R3.
- R5 — Codes par téléphone : SMS puis WhatsApp, d'après `GET /auth/methods` ; un canal indisponible
  est grisé « Bientôt disponible » et ne fait rien ; si la liste ne peut pas être lue, la ligne est
  cachée. Aucune liste écrite en dur. SMS disponible → l'écran actuel téléphone puis code ;
  WhatsApp disponible → le lien de FEAT-008 puis le même écran de code.
- R6 — Messages : ceux de FEAT-020 (`accountErrorMessage`), par exemple « E-mail ou mot de passe
  incorrect. » ou « Trop de tentatives. Réessayez dans 15 minutes. ».
- R7 — MFA : inchangée. Aucun moyen de connexion ne la demande pour ouvrir une session
  (`apps/api/src/modules/auth/auth.service.ts:59-64`) ; elle protège les actions sensibles
  (`@RequireStepUp()`), y compris après une connexion par mot de passe.

## Scénarios

### SPEC-021-02-SC01 — codes par téléphone d'après le serveur

Critères : FEAT-021-AC05

- **Étant donné** `/auth/methods` qui déclare SMS et WhatsApp indisponibles ; puis SMS disponible ;
  puis la liste illisible
- **Quand** la ligne des codes par téléphone est calculée
- **Alors** deux boutons grisés « Bientôt disponible » (SMS, WhatsApp) ; puis SMS actif et WhatsApp
  grisé ; puis aucune ligne

### SPEC-021-02-SC02 — compte sans le rôle de l'application : rien n'est gardé

Critères : FEAT-021-AC01, FEAT-021-AC02, FEAT-021-AC03

- **Étant donné** une session obtenue pour un compte client (rôle `customer`) avec un jeton
  d'appareil
- **Quand** l'application admin, restaurant ou livreur la reçoit
- **Alors** elle ne garde ni la session ni le jeton, et affiche son message de refus (par exemple
  « Ce compte n'a pas accès à l'administration DJAFAT. »)

### SPEC-021-02-SC03 — appareil mémorisé par application

Critères : FEAT-021-AC01, FEAT-021-AC02, FEAT-021-AC03

- **Étant donné** une connexion réussie avec « Se souvenir de cet appareil » cochée
- **Quand** la personne se déconnecte puis se reconnecte dans la même application
- **Alors** le jeton gardé est envoyé avec l'e-mail et le mot de passe, et la connexion se fait sans
  code ; une autre application ne connaît pas ce jeton

### SPEC-021-02-SC04 — mot de passe oublié

Critères : FEAT-021-AC04

- **Étant donné** un membre de l'équipe dont l'e-mail est vérifié, avec ou sans mot de passe
- **Quand** il demande un code, puis saisit le code et un nouveau mot de passe valide
- **Alors** il est connecté (R3) ; un mot de passe trop court ou trop courant est refusé avant
  l'envoi, avec le message de FEAT-020

### SPEC-021-02-SC05 — la MFA protège toujours les actions sensibles [evidence: review]

Critères : FEAT-021-AC07

- **Étant donné** un administrateur connecté par e-mail et mot de passe
- **Quand** il lance une action protégée (rôle, suspension, remboursement)
- **Alors** l'API exige son code d'authentification (`STEP_UP_REQUIRED`), comme après un code
  téléphone : la session ouverte par `PasswordService` est la même que celle du code téléphone

## Erreurs et cas limites

- Mauvais e-mail ou mot de passe : 401 `INVALID_CREDENTIALS`, un seul message (FEAT-020).
- Trop d'essais : `RATE_LIMITED` ou `OTP_LOCKED`, messages de R6.
- Compte suspendu : `ACCOUNT_INACTIVE` (« Ce compte est suspendu. Contactez DJAFAT. »).
- E-mail non configuré sur le serveur : `EMAIL_UNAVAILABLE` (« Le message n'a pas pu partir… »).

## Contrats API et données

Aucune route nouvelle : `/auth/password/login`, `/auth/password/challenge/send`,
`/auth/password/challenge/verify`, `/auth/password/forgot`, `/auth/password/reset`,
`/auth/methods` (FEAT-008, FEAT-020). Nouveau : `packages/sdk/src/team-login.ts` — `phoneCodeButtons(methods)` (R5, construit sur
`channelButtons`), `acceptTeamSignIn` (R3), `teamPasswordLogin`, `teamVerifyCode` et
`teamResetPassword` (R1, R2, R4). _(v2, revue 1)_ : `teamResetPassword` applique
`validateNewPassword` avant tout envoi (réponse `invalid` avec les erreurs de champ) ;
`teamVerifyPhoneCode` fait passer le code par téléphone par le même contrôle R3 ;
`TeamSessionKeeper` porte le message de refus de l'application (`deniedMessage`) et, pour les
consoles, `clearSession`, appelé au refus ; deux méthodes d'adaptateur du SDK pour les routes
existantes du code par téléphone : `requestPhoneLoginCode` (`/auth/otp/request`) et
`verifyPhoneLoginCode` (`/auth/otp/verify`, `/auth/whatsapp/verify`).

## Autorisations

Le contrôle de rôle côté application (R3) n'est qu'un confort d'affichage ; l'API vérifie les rôles
de chaque route (`@RequireRole`), comme aujourd'hui.

## Hypothèses et questions ouvertes

- Pas de « code seul par e-mail » dans les applications d'équipe : l'utilisateur a choisi e-mail et

  (FEAT-021-Q04).
