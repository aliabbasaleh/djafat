# SPEC-021-05 — Bascule : SMS coupé sur le serveur

## Comportement observable

La documentation de déploiement (`infra/deploy/README.md`) et celle des comptes externes
(`docs/39-comptes-externes.md` §1) décrivent comment passer du SMS de test du serveur à la
connexion par e-mail, dans un ordre qui ne laisse personne dehors.

## Règles métier

- R1 — Ordre : (1) l'e-mail marche (`EMAIL_PROVIDER=smtp`, Gmail officiel, `EMAIL_FROM` vide) ;
  (2) chaque membre de l'équipe a un e-mail vérifié et un mot de passe — « Mon profil » sur le site
  tant que le code téléphone marche encore, ou « Mot de passe oublié ? » dans son application si
  son e-mail est déjà vérifié —, ce qu'une requête en lecture seule contrôle : elle ne doit
  renvoyer aucun compte actif ayant un rôle autre que `customer` sans `email_verified_at` ou sans
  `password_hash` ; (3) `SMS_PROVIDER=disabled`, et `SMS_HTTP_URL`, `SMS_HTTP_API_KEY` mis en
  commentaire (pas effacés) dans `.env.prod` ; (4) relance de l'API ; (5) contrôle :
  `/auth/methods` répond `sms` indisponible, et chaque application se connecte par e-mail.
  _(v2 : requête de contrôle et lignes commentées, revue 1, constats n° 2 et 6)_
- R2 — Retour en arrière : `SMS_PROVIDER=http`, et les deux lignes décommentées (`SMS_HTTP_URL` vaut
  `http://mock-sms:4020/send` en mode démo, `SMS_HTTP_API_KEY` est vide), puis relance de l'API.
- R3 — Le jour où DJAFAT a une vraie API SMS : `SMS_PROVIDER=http` avec ses réglages, sans changer
  le code (docs/39 §1).
- R4 — Pourquoi le mot de passe compte (décision FEAT-021-Q11) : sur un compte sans mot de passe,
  une session volée suffit pour changer l'e-mail puis poser un premier mot de passe
  (`me.controller.ts`, `@RequireAuth()` seul) ; tant que le SMS marche, le titulaire garde la
  connexion par téléphone, après la coupure non. Une fois que chaque compte d'équipe a un mot de
  passe, ces deux actions demandent le mot de passe actuel (SPEC-020-12 R1, SPEC-020-05). Un code
  d'authentification (step-up) sur ces actions pour les rôles à MFA reste un renforcement à venir
  (T-612). _(v2)_

## Scénarios

### SPEC-021-05-SC01 — la procédure est complète et dans l'ordre [evidence: review]

Critères : FEAT-021-AC08

- **Étant donné** `infra/deploy/README.md` et `docs/39-comptes-externes.md` après la feature
- **Quand** ils sont relus
- **Alors** ils donnent les cinq étapes de R1 dans cet ordre, avec la requête de contrôle de
  l'étape (2), le retour en arrière complet (R2) et le branchement d'une vraie API (R3), sans aucun
  secret

### SPEC-021-05-SC02 — la requête de contrôle repère les comptes d'équipe à risque [evidence: manual]

Critères : FEAT-021-AC08

- **Étant donné** une base avec des comptes d'équipe actifs sans e-mail vérifié ni mot de passe, et
  d'autres qui ont les deux
- **Quand** la requête de l'étape (2) est lancée en lecture seule
- **Alors** elle liste les premiers et aucun des seconds ; tant qu'elle renvoie une ligne, le SMS
  n'est pas coupé

## Erreurs et cas limites

Un membre de l'équipe sans e-mail vérifié au moment de couper le SMS ne peut plus se connecter,
et un compte d'équipe sans mot de passe resterait exposé (R4) : la requête de l'étape (2) les
liste tous les deux ; un compte suspendu n'y figure pas (il ne peut pas se connecter), il lui faudra
un e-mail vérifié et un mot de passe avant d'être réactivé.
